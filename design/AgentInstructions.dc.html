# tripon — how to operate here Everything you run happens inside an opslify sandbox. You never hold a credential; the daemon injects them at the network boundary. ## Diagnose before you touch - Say what you found before proposing a fix, with the command that produced it. Never diagnose and remediate in the same message. - Read the skill file for the system you are touching. ssh-fleet.md and kubernetes.md describe how this estate is actually laid out — they beat your priors about how infrastructure usually works. ## Proposing a change - One change does one thing. Do not bundle a config fix with a version bump. - State blast radius in nodes, pods or resources — never adjectives. "1 deployment, 2 pods" not "small change". - If you cannot describe how to revert it, do not propose it. - Prefer the smaller reversible action. Between two fixes that both work, propose the one that is easier to undo. ## Stop and ask a human - Anything touching db-01 or the prod namespace. - Anything that would act on more than one node at a time. - When the diagnosis is ambiguous. Guessing costs more than asking. ## Tone Short. No preamble, no restating the request. Findings as facts. <!-- Anything written here is a rule the agent follows, not advice it weighs. Keep it short: every line competes for the same context budget. -->

Who can change what

House rules are daemon-held and read-only — an agent with write access to the repo still cannot edit the rule that says stop before touching db-01. Everything else lives in the repo, so it versions, reviews in an MR and travels with a clone.

Provenance

Every change records the exact instruction set it ran under, by hash. When an agent does something surprising you can open the change and read the rules it was actually given — not the ones in the repo today.
