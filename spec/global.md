# Opslifyd — Global Orchestration Spec

> **This is the orchestrator agent's entrypoint. Read this file first, every task.**
> It is the single source of truth that references every other document. Never build from memory — always resolve the reference chain below.

---

## 0. What this document is

`global.md` is the map. It tells the orchestrator agent:
1. **Why** we build (→ [goal.md](goal.md), [mission.md](mission.md))
2. **What** the system looks like (→ [architecture.md](architecture.md))
3. **What** to build, in what order (→ [phases/](phases/))
4. **Who** does each job and **how** (→ [best-practices/](best-practices/))
5. **When** a task is done (→ [§4 Definition of Done](#4-definition-of-done))

The orchestrator does not write code. It selects the next task, routes it, and enforces the workflow.

**Anti-hallucination rule:** [graph.json](graph.json) is generated by [tools/specgraph.py](tools/specgraph.py) from the feature files — it is the machine-readable source of truth for *what depends on what* and *what to build next*. The orchestrator reads `topological_order` and each node's `depends_on_resolved` from it rather than reasoning about order. **Regenerate it (`python3 spec/tools/specgraph.py`) after any change to a feature's `Depends on:` / `Blocks:` / `Status:`, and never hand-edit `graph.json` or `graph.mmd`.** The generator also fails on dependency cycles, dangling references, and features referenced but not specced — run it in CI.

**Rule:** a feature spec references its phase README; a phase README references this file; this file references goal/mission/architecture. Any agent unsure of scope walks *up* the chain until resolved. Never invent scope not derivable from the chain.

## 2. The three-agent workflow (+ human gate)

```
                 ┌──────────────────────────────────────────────┐
                 │  ORCHESTRATOR                                 │
                 │  reads global.md → picks next ready feature   │
                 │  from the active phase → assigns builder      │
                 └───────────────┬──────────────────────────────┘
                                 │ hands feature spec
                                 ▼
                 ┌──────────────────────────────────────────────┐
                 │  BUILDER (senior)                             │
                 │  Go for P0–P4 & UI · Rust for P5 secret paths │
                 │  implements to spec + tests + self-review     │
                 └───────────────┬──────────────────────────────┘
                                 │ hands diff + evidence
                                 ▼
                 ┌──────────────────────────────────────────────┐
                 │  QA (senior)                                  │
                 │  verifies against acceptance + QA checklist   │
                 │  runs escape/red-team suite · security review │
                 └───────────────┬──────────────────────────────┘
                                 │ pass → escalate
                                 ▼
                 ┌──────────────────────────────────────────────┐
                 │  MANUAL APPROVAL (you)                        │
                 │  final sign-off → feature marked `approved`   │
                 └──────────────────────────────────────────────┘
```

Failure at any stage routes **back one step** with written reasons. QA never fixes code; it reports. Builder never self-approves. Orchestrator never writes code.

### Agent roster

| Agent | Level | Language | Responsibility |
|---|---|---|---|
| **Orchestrator** | — | — | Task selection, routing, workflow enforcement, status tracking. Reads only. |
| **Builder (Go)** | Senior | Go | P0–P4, P6, local UI. Sandbox lifecycle, MCP, trace, policy, packaging. |
| **Builder (Rust)** | Senior | Rust | P5 secret-critical paths only: credential broker core + L7 egress proxy. |
| **QA** | Senior | Go/Rust read | Verification, red-team/escape suite, security review, acceptance sign-off. |

**Why the language split:** the container/security ecosystem (gVisor, containerd, Podman bindings, cosign/sigstore, Dagger, official MCP Go SDK) is Go — so Go is primary. Rust is used only where plaintext secrets live in memory (broker, egress proxy), for memory-zeroing and safety. See [architecture.md §Stack](architecture.md).

## 3. Task lifecycle & status

Each feature file carries a `Status:` field. The orchestrator advances it:

```
todo → in-progress → qa → awaiting-approval → approved
          │              │          │
          └── (fail) ◄────┴── (fail)─┘   routes back with reasons
```

- **todo** — ready; dependencies (`Depends on:`) are all `approved`.
- **in-progress** — assigned to a builder.
- **qa** — builder handed diff + evidence; QA verifying.
- **awaiting-approval** — QA passed; queued for your manual sign-off.
- **approved** — you signed off. Only now do dependent features unblock.

The orchestrator picks the next `todo` whose dependencies are all `approved`, respecting phase order (never pull a P4 feature while P1 is unfinished unless explicitly parallel-safe and marked so).

## 4. Definition of Done (a feature is `approved` only when ALL hold)

1. Every **Acceptance criterion** in the feature file passes, demonstrably (evidence attached).
2. Every item in the feature's **QA checklist** is checked.
3. Relevant **red-team / escape scripts** pass in CI (security criteria are automated tests — see [shared-engineering.md](best-practices/shared-engineering.md)).
4. Code meets [builder.md](best-practices/builder.md) standards; QA meets [qa.md](best-practices/qa.md).
5. No secret, token, or plaintext credential appears in logs, traces, or test output.
6. Docs/interfaces updated if the feature changed a shared interface (`Runtime`, `SecretBackend`, `TraceSink`, `EnvBuilder`).
7. **You** manually approved.

## 6. Convention: expanding later phases

P0 and P1 features are written as **individual files** in `features/` at full implementation depth — they are built first. P2–P6 phase READMEs carry their features **inline at spec level**. When the orchestrator activates a later phase, its **first task is to split that phase's inline features into individual `features/F*.md` files** at full depth (builder input, tools, data structures, acceptance, QA checklist), using the P0/P1 files as the template. This keeps deep detail honest — written when we know enough to write it, not guessed months ahead.

## 7. Two locked architecture decisions (never re-litigate without human sign-off)

- **D1 — Nix/devbox is a BUILD-TIME env composer only.** Tools are resolved + locked + signed into a read-only layer. No installs inside the live sandbox.
- **D2 — Isolation ladder:** `local-docker` (runc) / `local-hardened` = **gVisor+Podman, the default hero** / `cloud-microvm` (Firecracker, paid managed, built last). One `Runtime` interface, `location` = local|remote.
