# Manual test — F5.7 Broker egress integration (credential-blind GitLab)

**Feature:** [../phases/p5-broker/features/F5.7-broker-egress-integration.md](../phases/p5-broker/features/F5.7-broker-egress-integration.md)
**Status when written:** code-complete + self-QA'd; pending independent QA-agent pass + this real-host sign-off.

## What F5.7 does (what you're verifying)
Wires the F5.2 L7 egress proxy into the live session lifecycle so a granted tool call inside the sandbox reaches the real host with the daemon-injected auth header — **and the agent never sees the token**.

- At session create, if the session's **resolved** policy both **grants** a cred and **egress-allows** its host, the daemon builds a **per-session** `egressproxy.Proxy` + a **fresh per-session CA** + a loopback listener, and routes the sandbox through it via env:
  - `HTTPS_PROXY`/`HTTP_PROXY=http://<proxy-addr>`, `NO_PROXY=localhost,127.0.0.1,169.254.169.254`
  - `CURL_CA_BUNDLE`/`SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`/`GIT_SSL_CAINFO=/workspace/.opslify-ca.pem` (daemon-written)
- The token is added by the proxy on the **upstream leg** only. The sandbox env, the CA file, and the trace carry **no token**.
- **Fail-closed / opt-in:** no `egress_inject` rule for the session's (host, cred) ⇒ no proxy, no proxy env, F1.4 default-deny unchanged. A proxy/resolve failure injects no header and no raw-secret fallback. A workspace can never add/widen an egress-inject host (F4.1).
- **Agent-writable CA is safe:** the CA file lives in `/workspace` (agent-writable). Overwriting it only breaks the agent's own TLS to the proxy (self-DoS) — it cannot thereby extract the token, which rides the upstream leg regardless of the client's trust store.

## Level 2 — LIVE host demo (real sandbox → real gitlab.com)
Requires: a real host where the daemon can program egress and the sandbox can reach the daemon's loopback/bridge address (podman/gVisor networking). Read the caveats below FIRST.

### 1. Seed the secret (never in config, never in the sandbox)
```bash
export OPSLIFY_VAULT_KEY=$(openssl rand -hex 32)   # 32-byte master key (env only)
opslify secrets add gitlab-token                    # paste a real GitLab PAT (api scope)
```

### 2. Daemon config — `egress_inject` + a matching policy grant
`/etc/opslify/config.yaml` (daemon-authoritative — a workspace can never add/widen this):
```yaml
egress_inject:
  - host: gitlab.com
    secret_ref: gitlab-token
    header_name: PRIVATE-TOKEN
    header_format: "%s"        # PRIVATE-TOKEN: <raw>  (use "Bearer %s" for Authorization APIs)
```
Default policy (`policy_file:`) must both **grant the cred** and **egress-allow the host** (the rule only lights up when the RESOLVED policy has both):
```yaml
egress:
  domains: [gitlab.com]
creds:
  - name: gitlab-token
    provider: gitlab
```

### 3. Base image needs curl + CA certificates
```bash
opslify init            # ensure the sandbox base has `curl` and `ca-certificates`
```

### 4. Run the daemon (egress leg for the daemon→gitlab.com hop)
The sandbox→proxy leg is loopback/bridge; the **daemon→gitlab.com** leg must be permitted by F1.4. Either allowlist `gitlab.com` for the daemon's own egress, or for a first smoke test run with egress unenforced:
```bash
sudo OPSLIFY_VAULT_KEY=$OPSLIFY_VAULT_KEY opslifyd --insecure-no-egress     # dev only; never production
```
Look for the log line: `F5.7 credential-blind egress inject active rules=1` and, per session, `egress credential-blind HTTP path active`.

### 5. Prove it from inside the sandbox (via MCP / CLI)
```bash
# the granted call succeeds WITH the injected token:
curl -s "https://gitlab.com/api/v4/projects?membership=true" | head -c 300
#   => a JSON array of YOUR projects (authenticated)

# the token is NOWHERE in the sandbox:
env | grep -i token            # => nothing (only HTTPS_PROXY + CURL_CA_BUNDLE set)
env | grep -i PRIVATE-TOKEN    # => nothing
cat /workspace/.opslify-ca.pem | head -1   # => -----BEGIN CERTIFICATE-----  (a cert, not a secret)
grep -R "$(: your PAT)" /proc/self/environ /workspace 2>/dev/null   # => nothing
```
Expected: the API returns your projects, while every in-sandbox probe (`env`, the CA file, `/proc`) shows **no token**. On the wire to gitlab.com the `PRIVATE-TOKEN` header is present — added by the daemon at the boundary.

### 6. Fail-closed spot checks
- A host with **no** `egress_inject` rule (e.g. `curl https://example.com`) gets **no** `HTTPS_PROXY` route and stays under F1.4 default-deny.
- Remove the `creds` grant (or the egress domain) from the policy ⇒ no proxy is built, no `HTTPS_PROXY` env, and the call is not authenticated.
- Overwrite `/workspace/.opslify-ca.pem` with garbage ⇒ the agent's own `curl` to the proxy fails TLS (self-DoS); it still cannot read the token.

## Honest scope / caveats (integration-gated)
- **podman/gVisor networking is the gating variable.** The in-sandbox→proxy reachability depends on the sandbox being able to reach the daemon's pinned loopback/bridge address, and on the daemon→gitlab.com egress leg being allowlisted (or `--insecure-no-egress`). These are **environment-dependent** and are **NOT** unit-covered — Level 1 unit-tests the WIRING (proxy built on grant, env injected, CA written, no token, teardown, fail-closed) against the fake runtime.
- gVisor sharp edges (partial iptables, no host-network) can affect how the sandbox routes to the proxy address; if the sandbox cannot reach the proxy, `curl` fails to connect (an `egress`-layer failure, not a leak).
- The proxy TLS-terminates `gitlab.com` with the per-session CA; hosts that must not be MITM'd (checksum/signature verification) belong in `never_mitm`/F5.5, not here.
- Non-HTTP egress is unchanged (F1.4 default-deny + DNS-pinned).
