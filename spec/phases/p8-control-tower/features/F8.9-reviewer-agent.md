# F8.9 — Reviewer agent (adversarial review of a Change)

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F8.4, F8.5, F8.6 · **Blocks:**

## Goal
Before a human sees a proposed Change, have a **second, independent agent try to find what is wrong
with it**. This is the one place P8 adopts multi-agent, because here the second agent's independence is
the point — see `spec/decisions/D1-agent-topology.md`.

## Why this works here specifically
The **Change (F8.6) is already a complete handoff artifact**: intent, pinned diff, policy decision,
blast radius, prepared inverse, trace. The reviewer needs nothing from the proposer's context, so the
usual multi-agent failure — a lossy handoff that drops the "why" — does not apply. The artifact *is*
the interface.

## Scope
**In:** an optional per-environment reviewer binding (may use a different, cheaper or stronger model
than the operator agent, via F8.5); a review run over a proposed Change producing a verdict
(`concerns` / `no concerns`) with specific, cited objections; the verdict attached to the Change and
shown to the human approver. Prod may **require** a review before the approval prompt appears.
**Out:** the reviewer approving or denying anything (it advises; humans decide); reviewer access to
connections or any write path; a general agent-to-agent messaging bus.

## Acceptance criteria (testable)
- [ ] The reviewer runs in a **read-only** session with **no connections attached** and cannot exec against infrastructure.
- [ ] It receives only the Change artifact + relevant skills — not the proposer's conversation.
- [ ] Its verdict is advisory: a `concerns` verdict never blocks by itself, and a `no concerns` verdict never removes a human approval gate.
- [ ] The verdict, the reviewing agent and its model are recorded on the Change and in the trace.
- [ ] An environment may require review before approval; a reviewer failure fails **closed** (no review ⇒ the gate stays, with the failure shown), never silently skipped.

## QA checklist
- [ ] The reviewer cannot mutate anything: no connections, no exec, no repo write (asserted, not reasoned).
- [ ] A `no concerns` verdict cannot auto-approve — approval remains a human action (auto-approval would be BLOCKING).
- [ ] Review adds no path for the proposer to influence the verdict beyond the artifact itself (no shared session, no shared context).
- [ ] Cost/latency is bounded and visible; a slow reviewer degrades to "review unavailable", not to a stalled Change.

## Security considerations
- A reviewer that can act is not a reviewer, it is a second operator. Read-only and connection-less is
  the invariant that keeps it a safety feature rather than a doubling of blast radius.
- Automation bias is the real risk: a green verdict must be presented as *one agent found no
  objection*, never as an endorsement, or it will erode the human approval it exists to strengthen.
