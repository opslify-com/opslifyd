# F8.6 — Change as the unit of work

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F4.3, F4.4, F8.1 · **Blocks:** F8.7, F8.8, F8.9

## Goal
Promote the P4 approval gate into a first-class, addressable object. A **Change** is the infrastructure
equivalent of a pull request — the thing humans review, the thing agents hand to each other, and the
thing the audit trail is organised around.

## Scope
**In:** a `Change` record — intent (human-readable), proposer (agent or human + model), environment,
policy decision + rule, preview/diff (hash-pinned where the tool supports it), planned steps with the
gated step marked, blast radius in counted resources, prepared **inverse**, resulting trace segment,
and status (proposed → previewed → awaiting approval → applying → applied | denied | failed |
reverted). Addressable by id; listable per project/environment; `opslify change ls|show|approve|deny|revert`.
**Out:** cross-environment promotion workflow (follows once Changes exist); automatic rollback without
an operator action.

## Why this object earns its place
Sessions are a runtime detail; humans do not review sessions. Reviewing, approving, auditing,
reverting, promoting and agent-to-agent handoff (F8.9) all need the *same* bundle of facts — so it is
one object, not five views over a trace.

## Acceptance criteria (testable)
- [ ] Every gated exec produces a Change with intent, diff, policy rule, blast radius and prepared inverse; approving it runs exactly the pinned plan (extends the F4.4 hash-pin).
- [ ] Blast radius is stated in **counted resources** (deployments, pods, hosts, files), never adjectives.
- [ ] A Change records the policy hash (F4.1), instruction-set hash (F8.4), agent + model (F8.5) and connection refs used — refs, never values.
- [ ] `revert` applies the prepared inverse where the kind supports it (k8s manifest re-apply, git revert, target-group re-add) and refuses honestly where it does not (e.g. Terraform state), rather than pretending.
- [ ] The Change's trace segment verifies under `opslify verify`.

## QA checklist
- [ ] A Change cannot be approved into a *different* plan than the one previewed (re-verify the pin at apply; TOCTOU is BLOCKING).
- [ ] Denied and timed-out Changes are terminal and auditable; nothing runs after a deny.
- [ ] Revert is never silently unavailable — the UI states whether an inverse exists **before** approval, not after failure.
- [ ] No regression to F4.3 approvals or F4.4 dry-run.

## Security considerations
- The pinned preview is a security control, not a convenience: approval is meaningless if the applied
  plan can differ from the reviewed one.
- "Prepared inverse" must be honest. Claiming revertibility that does not exist is worse than
  admitting the limit, because it changes what an operator is willing to approve.
