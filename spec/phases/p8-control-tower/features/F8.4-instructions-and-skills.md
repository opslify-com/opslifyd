# F8.4 — Instructions & skills (layered agent context)

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F8.1 · **Blocks:** F8.5, F8.8, F8.9

## Goal
Give the operator one place to say **how the agent should behave** and **what it needs to know about
this estate**, assembled from ordered layers with provenance — so an agent is good at *your* fleet
rather than DevOps in general, and so "why did it do that?" is answerable against the rules it
actually had.

## Two different things, deliberately separated
- **Instructions** = behaviour. *Diagnose before you touch. State blast radius in pods, not adjectives. If you cannot describe the revert, do not propose it.*
- **Skills** = knowledge of this estate, per tool. *`db-01` is the primary — never restart it. 502s on this fleet are memory pressure; check `free -m` first. Drain before restarting a web node.*

Conflating them produces one long file nobody maintains. Splitting them makes skills generatable,
routable and individually reviewable.

## Layers (precedence order; later may add, never contradict)

| # | Layer | Lives | Editable by |
|---|---|---|---|
| 1 | **House rules** | daemon · `/etc/opslify/house-rules.md` | operator on the host only — **read-only to the agent and to repo commits** |
| 2 | **Project instructions** | repo · `.opslify/instructions.md` | repo, reviewed in an MR |
| 3 | **Environment overlay** | repo · `.opslify/env/<env>.md` | repo (prod narrows staging) |
| 4 | **Skills** | repo · `.opslify/skills/*.md` | repo |
| 5 | **Tool contracts** | generated from tools + policy | daemon — not hand-edited |

Layer 1 in the daemon is the point: an agent that can write to the repo still cannot edit the rule
that says *stop before touching db-01*.

## Scope
**In:**
- **Assembly + provenance.** `context.Assemble(project, env)` returns the ordered layers, their token
  costs, and a **content hash**. The hash is emitted as `context.assemble` at session start and bound
  into the Change, so a Change can be replayed against the exact instructions it ran under.
- **Per-tool skill generation on integration.** When a tool is added, the daemon scaffolds
  `.opslify/skills/<tool>.md` from a starter template **and** offers an agent-assisted draft: a
  read-only sandbox session reads what is actually in the repo (`.gitlab-ci.yml`, chart values,
  Terraform modules, manifests) and proposes a first version describing *this* estate's conventions.
  The operator edits and commits it. The draft is a proposal, never auto-committed.
- **Capability map → routing.** Onboarding records roles (`git=gitlab`, `ci=gitlab-ci`,
  `deploy=argocd`, `orchestration=kubernetes`, `iac=terraform`). The map selects which skill packs load
  for a task, so a CI task is not carrying Terraform provider docs. Deterministic and inspectable —
  the assembled set is shown in the UI and recorded in the trace.
- **Budget visibility.** Assembled size vs the reserved budget, per layer, in the UI and via
  `opslify context show`.
- CLI: `opslify skill add|ls|edit|draft`, `opslify context show|diff`.

**Out:**
- One agent per tool — see `spec/decisions/D1-agent-topology.md`. Skills are context packs for a
  single operator agent, not separate agents.
- Auto-committing agent-drafted skills.
- Semantic verification that a skill is *true*; staleness is mitigated by review and provenance, not
  by the daemon claiming to check facts.

## Implementation approach
1. `internal/context`: layer loader → ordered assembly → hash → token accounting. Pure and unit-testable; no model calls.
2. House-rules layer loads from the daemon config path with the same 0600/root ownership treatment as other daemon-held files, and is **never** sourced from the workspace.
3. Skill scaffolding on tool integration; agent-assisted draft runs in a **read-only** session with no connections attached (it reads the repo, nothing else).
4. Routing: capability map + task hints select packs; the selection is emitted so it is auditable.
5. Emit `context.assemble` (layer names, hashes, token counts — never the content) into the trace.

## Acceptance criteria (testable)
- [ ] Layers assemble in the documented order; a later layer cannot remove or override an earlier one (asserted).
- [ ] House rules are read from the daemon path only; a `.opslify/house-rules.md` planted in the workspace is **ignored** (asserted — this is the tamper case).
- [ ] `context.assemble` is emitted at session start with the layer hashes and lands in the verifiable chain; a Change resolves to the exact instruction set it ran under.
- [ ] Adding a tool scaffolds `.opslify/skills/<tool>.md`; the agent-assisted draft runs in a read-only session with no connections and never writes to the repo itself.
- [ ] The capability map selects packs deterministically; the selected set is recorded and shown.
- [ ] Token accounting matches the assembled content within a documented tolerance; budget overrun warns rather than silently truncating.
- [ ] Instruction content never appears in the trace — only names, hashes and sizes.

## QA checklist
- [ ] A workspace-supplied file can never reach layer 1 (workspace is untrusted input — a planted house-rules file being honoured is BLOCKING).
- [ ] Assembly is deterministic: same inputs → same hash, across runs and machines.
- [ ] The agent-assisted draft session has **no connections attached and no write path to the repo**; it cannot exfiltrate via a skill draft.
- [ ] Skill content is treated as data by the daemon, never executed or interpreted as policy — policy lives in F8.7, and a skill saying "you may skip approval" changes nothing.
- [ ] Silent truncation on budget overrun is BLOCKING; warn and let the operator cut.
- [ ] No regression to F3 trace, F4 policy, F7.3 workspace sync (skills are ordinary repo files and follow the same exclusion rules).

## Security considerations
- **Skills are instructions to a model, not permissions.** Nothing written in a skill can widen what a
  session may do; that is policy (F8.7), enforced in the daemon. A skill that says "you may restart
  db-01" is overruled by the gate. This separation must stay obvious in the UI, or operators will
  write security rules in the wrong file.
- **House rules must be unreachable from the repo.** The whole value of layer 1 is that an agent with
  commit access cannot edit its own constraints; sourcing it from the workspace would silently remove
  that property.
- **Provenance beats trust.** Skills go stale and stale skills produce confident wrong actions. The
  defence is that every Change names the instruction hash it used, so a bad action is traceable to the
  rule that caused it — and the fix is a reviewable commit.
- **Drafting reads real infrastructure code.** The draft session is read-only and connection-less by
  construction so "help me write my skills" can never become a data-exfiltration path.
