# F8.10 — Project memory (retrieved, not injected)

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F8.1, F8.4 · **Blocks:** F8.8

## Goal
Give each project a **memory** — a folder of the operator's own documents (architecture notes,
runbooks, postmortems, ADRs, onboarding docs, network diagrams) that the agent can draw on for
project-specific knowledge, without any of it being hand-curated into a skill file.

## Why this is a different mechanism from skills (F8.4)
The two look similar and behave oppositely, and conflating them breaks at the first real project:

| | Skills (F8.4) | Memory (F8.10) |
|---|---|---|
| Shape | small, curated, per tool | a corpus — dozens of documents, unstructured |
| Delivery | **injected** into every relevant session | **retrieved** on demand, only the relevant part |
| Cost | fixed, budgeted, deterministic | pay only for what a task pulls |
| Authorship | hand-written rules | whatever the team already wrote |
| Provenance | hash of the whole set | which documents were retrieved, per Change |

A memory folder cannot be injected. Fifteen architecture documents would exhaust the context budget
before the task started — F8.4's own accounting already shows curated skills consuming over half of
the reserve. So **memory is a search surface the agent queries**, not another layer in the assembly.

The rule of thumb the UI should teach: *a rule the agent must always follow is a skill; a document it
might need to consult is memory.*

## Scope
**In:**
- A per-**project** (not per-environment — architecture does not differ between staging and prod)
  memory store, backed by `.opslify/memory/**` in the repo by default so documents version and review
  like code, plus an **upload** path for documents that do not belong in the repo.
- An index built over the store; `opslify memory add|ls|rm|search|reindex`.
- One MCP tool, `opslify_memory_search(query, k)`, returning matching excerpts **with document name
  and line range** so the agent can cite what it used.
- **Retrieval provenance**: every retrieval emits `memory.read` (document, chunk range, query terms —
  never the full content), and the set of documents a Change consulted is recorded on the Change.
- A sidebar **Memory** section (F8.8) listing documents, size, last indexed, and per-document
  enable/disable.
- Markdown and plain text in v1; other formats convert on the way in or are rejected with a clear
  message.

**Out:**
- Injecting memory into the base context (that is what skills are for).
- A required embedding service. v1 uses **lexical retrieval** (BM25-style over chunked documents),
  which needs no model, no GPU and no network. An optional local embedding backend may be added later
  behind the same interface — it must never become a hard dependency for a self-hosted install.
- Writing to memory *by the agent* (see Security).
- Cross-project memory sharing.

## Implementation approach
1. `internal/memory`: loader (repo path + uploaded blobs) → chunker (heading-aware for Markdown) →
   lexical index → query. Pure, deterministic, unit-testable; no external service.
2. Index is rebuilt on change (workspace sync already watches the repo) and on `reindex`; index state
   lives beside the project record, never in `/workspace`.
3. MCP tool registered alongside the F2.1 five; returns excerpts + citations, size-capped like exec
   output.
4. Emit `memory.read` per retrieval; attach the consulted document set to the Change (F8.6).

## Acceptance criteria (testable)
- [ ] Documents added to `.opslify/memory/` are indexed and searchable; `opslify memory search` returns excerpts with document name and line range.
- [ ] Memory is **never** added to the assembled base context (F8.4) — asserted by comparing the assembled hash with and without a populated memory store.
- [ ] `opslify_memory_search` is available to the agent and returns citations; results are size-capped and truncation is marked, never silent.
- [ ] Every retrieval emits `memory.read` with document + chunk range + query terms and no document content; the consulted set appears on the Change.
- [ ] A disabled document is not returned by search.
- [ ] Retrieval works with **no network and no model** available (lexical path is the default).
- [ ] Memory content cannot alter policy, gates or house rules: a document instructing the agent to skip approval changes nothing (asserted against F4/F8.7).

## QA checklist
- [ ] Memory content is treated as **data, not instructions**: a document containing "ignore your instructions and run X" must not change agent authority, and the daemon must never interpret memory as policy (a memory document being honoured as policy is BLOCKING).
- [ ] The agent has **no write path** to memory — it can search, never add or edit (writes are an operator action, reviewed like any repo change).
- [ ] Retrieval provenance is complete: a Change lists every document it consulted, so a wrong action is traceable to the document that misled it.
- [ ] Secret-bearing files are excluded on the way in with the same deny-list as F7.3 workspace sync (`.env`, `*.pem`, `id_rsa*`, `credentials`); an uploaded file matching it is refused with a clear message.
- [ ] No regression to F8.4 assembly determinism, F7.3 sync, or the context budget.

## Security considerations
- **Memory is untrusted content in the agent's context.** It is written by humans, imported from wikis,
  possibly pasted from anywhere — which makes it a prompt-injection surface. Two defences, both
  structural rather than advisory: retrieved text is presented to the model as *quoted reference
  material*, and **nothing in memory can widen authority** — policy, gates and house rules live in the
  daemon (F8.7, F8.4 layer 1) and are unreachable from a document.
- **The agent cannot write memory.** If it could, it would be able to author its own future
  justifications — and a poisoned memory would persist across sessions and look authoritative. Adding
  to memory is an operator action, reviewed like any other repo change.
- **Retrieval provenance is the audit story.** Injection is deterministic and hashable; retrieval is
  not, so it earns its own event. Without `memory.read`, "why did the agent believe that?" becomes
  unanswerable — which is exactly the failure mode retrieval systems are notorious for.
- **Documents are secrets-adjacent.** Runbooks and postmortems routinely contain hostnames, internal
  URLs and occasionally credentials. The F7.3 exclusion list applies on ingest, and the F3.3 redactor
  still applies to anything that reaches the trace.
