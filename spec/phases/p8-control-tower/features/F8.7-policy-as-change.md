# F8.7 — Policy editing as a Change

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go + SPA) · **Depends on:** F4.1, F8.1, F8.6 · **Blocks:** F8.8

## Goal
Let operators create and update guardrails — egress allowlists, approval gates, preview rules, session
limits — per environment, from the UI and CLI, **without editing YAML on the host and restarting the
daemon**. And make the edit itself governed: widening the guardrails is a Change.

## Scope
**In:** an editable resolved-policy view per environment; add/remove egress hosts (resolve + pin);
add/edit gates, preview rules and session limits; `opslify policy show|diff|allow-egress|gate`. A
**widening** edit creates a Change (F8.6) requiring approval; a **narrowing** edit applies immediately.
Precedence surfaced: daemon → project → environment → workspace, each able only to narrow.
**Out:** editing daemon-held **house rules** from the UI (locked by design — host-side only); policy
templating/inheritance beyond the four layers.

## Acceptance criteria (testable)
- [ ] Adding an egress host resolves and pins it, and takes effect for the **next** session; running sandboxes keep the policy hash they started with.
- [ ] A widening edit (new egress host, removed gate, longer TTL) creates a Change and does **not** apply until approved; a narrowing edit applies without approval and is still recorded.
- [ ] The workspace-supplied policy can never widen the environment's (extends F4.1); clamps are recorded and visible.
- [ ] House-rule gates are rendered read-only and cannot be edited through any route.
- [ ] `opslify policy diff staging prod` reports the real difference between resolved policies.

## QA checklist
- [ ] Classification of widening vs narrowing is conservative: anything ambiguous is treated as **widening** and gated (a widening slipping through as narrowing is BLOCKING).
- [ ] No route edits house rules; no route bypasses the Change for a widening edit (including the CLI).
- [ ] Policy hash changes on every applied edit and is bound into subsequent sessions.
- [ ] No regression to F4.1 resolution or F1.4 default-deny egress.

## Security considerations
- **Guardrails that can be edited without governance are not guardrails.** Making a widening edit a
  Change is what stops an agent-or-human quietly opening egress to a host they need, and makes "who
  opened this, when, and who approved it" answerable a year later.
- Narrowing stays ungated deliberately: tightening in an incident must never wait for an approver.
