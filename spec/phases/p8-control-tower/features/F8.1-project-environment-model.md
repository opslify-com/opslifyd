# F8.1 — Project & environment model

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F2.2, F4.1 · **Blocks:** F8.2, F8.3, F8.4, F8.5, F8.6, F8.7

## Goal
Introduce the spine everything else in P8 hangs off: a **Project** that gathers what a body of work
needs, and **Environments** within it that carry the risk gradient (staging auto-approves what prod
gates).

## Scope
**In:** a `Project` record (name, repo, capability map of roles → tools) and `Environment` records
(name, policy overlay, connections, agent binding, workspace, session defaults). Durable storage
alongside the existing session store; project/environment scoping threaded through sessions,
connections, secrets, instructions and changes. CLI `opslify project create|ls|show`,
`opslify env add|ls|use`.
**Out:** multi-user ownership and RBAC (cloud plane); cross-project sharing beyond secrets by ref.

## Why environments are separate layers
Not headings inside one file. Prod must be able to **narrow** staging (stricter gates, fewer egress
hosts, a different agent) and the narrowing must be enforced by the daemon, not by convention. Merged
files make "which rules applied in prod?" a reading exercise instead of a lookup.

## Acceptance criteria (testable)
- [ ] A project owns ≥1 environment; a session is always created in exactly one environment and records both ids.
- [ ] An environment overlay may only **narrow** its project's policy; a widening attempt is clamped and the clamp is recorded (extends F4.1 narrows-not-widens).
- [ ] Connections, secrets refs, instructions and changes all resolve within a project/environment and are listable by it.
- [ ] Removing an environment tears down its sandboxes and connection artefacts; removing a project refuses while anything is live.
- [ ] Records survive a daemon restart and reconcile with running sandboxes.

## QA checklist
- [ ] No cross-environment leakage: a staging session cannot resolve a prod-only connection or secret grant.
- [ ] Project/environment ids appear in every trace event that is scoped to one, so audit can be filtered without inference.
- [ ] No regression to F2.2 workspaces or F4.1 policy resolution.

## Security considerations
- The environment is the **risk boundary**. If narrowing is advisory rather than enforced, the entire
  prod story is decoration — so clamping is daemon-side and recorded, never UI-side.
- Deleting a project must not orphan a live sandbox holding connections; teardown is ordered and fails
  closed.
