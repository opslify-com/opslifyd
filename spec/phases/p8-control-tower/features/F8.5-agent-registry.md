# F8.5 — Agent registry (bring your own agent)

**Phase:** P8 · **Status:** planned · **Owner:** Builder (Go) · **Depends on:** F2.1, F8.1, F8.4 · **Blocks:** F8.9

## Goal
opslify ships no model. Let the operator bind **any MCP-speaking command** — Claude Code, a local Qwen
via Ollama, Codex, a custom CLI — to a project and environment, with a fallback, and make the choice
visible everywhere it matters.

## Scope
**In:** an `Agent` record (name, command + args, transport, optional model hint, env allowlist) bound
per project/environment with a fallback; `opslify agent add|ls|use|test`; the bound agent surfaced in
the cockpit header and recorded in every session and Change; a connectivity test that reports tools
exposed and skills attached.
**Out:** proxying or hosting a model; billing/quota; prompt storage.

## Acceptance criteria (testable)
- [ ] An agent is bound per environment with a documented fallback; `opslify agent use` switches it without touching sandboxes already running.
- [ ] The bound agent's identity **and model hint** are recorded in `session.start` and in every Change, so a decision is attributable to a model.
- [ ] The MCP tool surface, policy gates and audit trail are **identical** whichever agent is bound (asserted by running the same scripted task under two registered agents).
- [ ] A custom command that fails the MCP handshake is reported as unusable at bind time, not at first task.
- [ ] Agent env is allowlisted: a registered command cannot inherit arbitrary daemon environment.

## QA checklist
- [ ] Switching agents cannot widen capability — the sandbox boundary, connections and gates are unchanged (a bound agent is not a trust level).
- [ ] No credential is passed to an agent process; a provider API key is a secret ref used by that command's own configuration, not injected by opslify into its env.
- [ ] A local agent (no egress) works with no cloud dependency at all.
- [ ] No regression to F2.1 MCP tools.

## Security considerations
- The registry must not become a privilege dial. Cheap-local vs strong-hosted changes cost, latency and
  **where prompts go** — never what the agent may do. If a future feature makes an agent binding grant
  capability, it belongs in policy (F8.7) with an approval, not here.
- Where prompts go is a real disclosure decision: the UI states plainly that a hosted agent sends
  command output off-host, and that a local agent does not.
