# F4.3 — Approval gates (human-in-the-loop)

**Phase:** P4 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F4.2, F3.2 · **Blocks:** F4.4

## Goal
When F4.2 classifies a command as `needs-approval`, **pause the exec**, surface an approval prompt to the human (local UI + cloud), and let them approve/deny with a comment — with a timeout that auto-denies. Critically, the **MCP tool returns a structured pending/denied status and never hangs the agent**.

## Scope
**In:** the `awaiting_approval` exec state + pause/resume machinery, an approval event pushed over the F3.2 stream to F3.5's UI (and cloud), the approve/deny + comment API, a config timeout (default 10m) → auto-deny, and the structured MCP/CLI response contract.
**Out:** the classification of *what* needs approval (F4.2), the diff shown beside the prompt (F4.4 provides it), auth/RBAC on *who* may approve (localhost trust model for F3.5; team-plane auth is cloud/F3.4).

## Implementation approach
1. **Pause:** on `needs-approval`, the exec enters `awaiting_approval` — the process is NOT spawned; a pending record `{session, exec_id, argv_summary, rule, requested_at}` is created and an `approval.requested` event pushed via F3.2 (so F3.5 renders a prompt live).
2. **Decide:** an API (`POST /v1/sessions/{id}/approvals/{exec_id}` → approve|deny + optional comment) resolves it; approve → the exec proceeds and runs; deny → the exec returns a structured denial. Each resolution emits a `policy.decision` (approved/denied, approver-comment) into the trace.
3. **Timeout:** a config TTL (default 10m) auto-denies a pending approval with reason `timeout`, so nothing hangs forever.
4. **Agent never hangs (the key contract):** the MCP `opslify_exec` tool returns immediately with a **structured** status — `pending` (with a handle to poll) or, on resolution, `approved`+output / `denied`+reason. The agent gets an actionable, typed result and can move on; it is never blocked on a synchronous human. Define whether the tool returns `pending` immediately (agent polls/re-calls) or blocks up to a short bound then returns `pending` — pick the non-hanging contract and document it.
5. **Idempotency/races:** a resolved approval can't be double-applied; a session that ends while pending cancels cleanly (auto-deny + `session.end`).

## Tools & libraries
Go, the F4.2 decision seam, the F3.2 SSE push + F3.5 UI (prompt render + approve/deny buttons — the slot F3.5 already reserved), the F2.1 MCP tool contract, a timer/clock (reuse the injected clock for testable timeouts).

## Acceptance criteria (testable)
- [ ] A gated command pauses in `awaiting_approval`; an `approval.requested` event reaches the local UI live.
- [ ] **Approve → the command runs and returns output; deny → the agent gets a denial with the reason/comment.**
- [ ] **Timeout (default 10m) → auto-deny** with reason `timeout`.
- [ ] The **MCP tool returns a structured pending/denied status and never blocks the agent indefinitely** (assert the tool returns within a bounded time with a typed status).
- [ ] Every approve/deny/timeout emits a `policy.decision` into the trace with the approver comment (redacted/chained).
- [ ] A session ending while an approval is pending cancels it cleanly (auto-deny, no leaked pending state).

## QA checklist
- [ ] Pause is real: the process is NOT spawned until approval (verified against the fake runtime — no Exec on pending/deny).
- [ ] Timeout uses the injected clock and is deterministic in tests; a late approval after timeout is rejected (no resurrection).
- [ ] Concurrency: two approvers / approve+deny race resolves once, deterministically; no double-spawn.
- [ ] The MCP non-hang contract holds under a never-answered approval (agent gets `pending`/`denied`, not a hang) — explicit test.
- [ ] Approval events + comments are redacted (F3.3) and chained (F3.1); a denied exec leaves an auditable trail.

## Security considerations
- **Fail-closed on ambiguity:** timeout, session end, daemon restart while pending → **auto-deny**, never auto-approve.
- The approve/deny API is a privileged control action; in the F3.5 localhost model it inherits the local-operator trust boundary (no auth in v1), and any remote approval must go through the authenticated cloud/team plane (F3.4) — never expose approve/deny to an unauthenticated network.
- The agent must not be able to self-approve: approval resolution comes from the human control plane (CLI/UI/cloud), never from within the sandbox or an MCP tool the agent controls.
