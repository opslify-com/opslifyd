# F4.4 — Dry-run interception (preview destructive ops)

**Phase:** P4 · **Status:** in-progress · **Owner:** Builder (Go) · **Depends on:** F4.3 · **Blocks:**

## Goal
Before a destructive infra command runs, **show what it would do**: rewrite `terraform apply` → a `plan` first and `kubectl delete/apply` → a server-side `--dry-run` diff, and surface that diff **beside the approval prompt** so the human approves with the actual change in front of them. Rewrite rules are extensible via policy.

## Scope
**In:** built-in rewrite rules for terraform + kubectl that produce a preview/diff, wiring the diff into the F4.3 approval prompt, and a policy-extensible rewrite-rule mechanism.
**Out:** approval mechanics (F4.3), classification (F4.2). Not a general infra simulator — a bounded set of known-tool previews plus a config hook.

## Implementation approach
1. **Built-in rewrites:**
   - `terraform apply` → run `terraform plan -out=<tmp>` first; capture the plan output/diff; the approved `apply` uses the saved plan file so what's approved is exactly what runs.
   - `kubectl apply`/`delete` → run with `--dry-run=server` first; capture the diff.
   The preview runs inside the SAME sandbox (same toolchain/creds context) so it's faithful.
2. **Diff beside the prompt:** the captured preview is attached to the F4.3 `approval.requested` event (redacted via F3.3) so F3.5's UI shows the diff next to approve/deny.
3. **Approve-runs-exactly-what-was-previewed:** for terraform, apply the saved plan file (not a fresh apply) so the diff and the executed change can't diverge; document the equivalent guarantee (or its limit) for kubectl.
4. **Extensible rules:** a policy `dry_run:` section maps a command pattern → a preview command template, so operators add their own (e.g. `helm upgrade` → `helm diff`). Validated by F4.1's schema.
5. **Failure handling:** if the preview command fails, surface that in the prompt (don't silently approve-without-preview); policy decides whether a failed preview blocks or just warns.

## Tools & libraries
Go, the F4.2 interceptor + F4.3 approval event, the `Runtime.Exec` seam (to run the preview in-sandbox), F3.3 redaction (diffs may contain secrets), F4.1 schema (for the `dry_run` rules).

## Acceptance criteria (testable)
- [ ] **A gated `terraform apply` produces a plan diff + approval prompt; approve applies the saved plan; deny returns the reason to the agent.**
- [ ] `kubectl apply`/`delete` in a gated session produces a `--dry-run=server` diff surfaced beside the prompt.
- [ ] The diff is attached to the approval event and rendered in the local UI (redacted).
- [ ] A policy-defined custom rewrite rule (e.g. `helm diff`) runs and previews.
- [ ] A failed preview does not silently approve — it surfaces the failure per policy (block or warn).

## QA checklist
- [ ] terraform: the approved apply uses the SAVED plan file, so the executed change equals the previewed diff (no TOCTOU drift) — tested against a fake/stubbed terraform.
- [ ] The preview runs in-sandbox with the same context, not on the host (no host escape via a preview command).
- [ ] Diffs are redacted (F3.3) before hitting the trace/UI (a plan can echo secrets/vars).
- [ ] Rewrite rules are pure/config-driven (no arbitrary host command injection from a workspace policy — the workspace-can't-widen invariant from F4.1 applies to `dry_run` rules too).
- [ ] Preview-failure paths are deterministic and fail-closed per policy.

## Security considerations
- **Preview must not have more privilege than the real command** — it runs in the same sandbox under the same policy/creds; a `dry_run` rule from an (untrusted) workspace policy must not be able to run an arbitrary host command or widen capability (inherits F4.1's narrow-only invariant).
- Diffs are sensitive (they can contain resource names, vars, secrets) → always redacted before trace/UI, and only ever shown on the redacted stream.
- The terraform saved-plan approach is a security feature: it closes the gap where an approved "apply" could do something different from the reviewed "plan."
