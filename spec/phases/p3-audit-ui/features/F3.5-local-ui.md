# F3.5 — Local UI (daemon-served, no cloud)

**Phase:** P3 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F3.2 · **Blocks:**

## Goal
A zero-install, **localhost-only** dashboard the daemon serves itself — `opslify ui` — that shows running sessions live, streams exec output, renders the event timeline, replays past sessions, and can **kill** a session, all with **no cloud connection**. This is the visibility surface for air-gapped/regulated buyers who can't use the cloud dashboard, and the "show running sessions in a UI" north-star ask.

## Scope
**In:** `opslify ui` (embedded SPA on `127.0.0.1:<port>`) and a lighter `opslify top` TUI, both consuming the **existing** session REST API (P1) + F3.2 SSE trace stream — no new backend. Views: live session list, streaming output (xterm.js), event timeline, replay, Kill button. An approval-prompt slot for when P4 lands.
**Out:** auth/RBAC, remote access, multi-user — those belong to the cloud/team plane (F3.4), not here. No new persistence.

## Implementation approach
1. **Serving:** `opslify ui [--port]` tells the daemon to serve a static SPA bundle **embedded via `embed.FS`** in the Go binary — nothing extra to install. **Bind `127.0.0.1` only**, no auth in v1 (localhost trust boundary; documented explicitly).
2. **Data:** the SPA calls the existing `GET /v1/sessions` for the list and `GET /v1/sessions/{id}/trace?from_seq=…` (F3.2 SSE) for live events + backfill. No endpoint duplication — same API the CLI uses.
3. **Views:** (a) session list — live state/tier/agent/age/TTL; (b) live terminal — xterm.js fed by `exec.output` events; (c) event timeline — `exec.start/end`, `file.write`, redaction markers; (d) replay — `from_seq=0` re-stream; (e) **Kill** button → existing `session kill` / `DELETE /v1/sessions/{id}`.
4. **TUI variant:** `opslify top` renders the same session list + selected-session stream in the terminal (Bubble Tea) for headless hosts; smaller surface, same data source.
5. **P4 seam:** leave a clearly-marked slot for approval prompts (`policy.decision` events + an approve/deny action) so P4 drops in without a redesign.

## Tools & libraries
Go `embed.FS` + `net/http`, xterm.js (vendored/embedded, no CDN), a minimal SPA (framework-light to keep the bundle small and self-contained), Bubble Tea (TUI), the existing session REST API + F3.2 SSE.

## Acceptance criteria (testable)
- [ ] `opslify ui` with **no cloud configured** shows running sessions live and updates as they change state.
- [ ] Exec output appears in the local UI **< 2s** after it happens in the sandbox.
- [ ] Replaying a finished session reproduces its full ordered event stream.
- [ ] The Kill button terminates a live session (reflected in the list + a `session.end` event).
- [ ] The UI binds `127.0.0.1` only — not reachable from another host.
- [ ] The SPA is fully self-contained (no external network fetch); works offline/air-gapped.

## QA checklist
- [ ] SPA bundle is embedded (no runtime CDN/asset fetch); verified by serving with the network blocked.
- [ ] SSE reconnect in the browser resumes from the last seen `seq` (no gaps/dupes in the rendered stream).
- [ ] Only the redacted stream is ever rendered (no raw-secret path from daemon → browser).
- [ ] Localhost bind is enforced in code, not just config; a non-loopback bind is rejected/documented.
- [ ] `opslify top` and `opslify ui` show consistent data from the same API.
- [ ] Killing/replaying is safe against a session that ended between list-render and action.

## Security considerations
- **Localhost-only, no auth in v1** is a deliberate trust boundary: the local UI assumes an operator on the host. Any remote/multi-user access must go through the cloud/team plane (F3.4) — the local UI must never be the thing exposed to a network.
- The UI is read-mostly plus Kill; it introduces **no new mutation path** beyond the existing session API, so it can't weaken the sandbox.
- It renders **redacted** events only (F3.3) — a shoulder-surfer or screenshot can't leak a secret the trace already scrubbed.
