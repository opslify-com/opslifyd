# F3.4 — Cloud dashboard

**Phase:** P3 · **Status:** deferred · **Owner:** Builder (Go daemon side) + existing web stack · **Depends on:** F3.2, F3.3 · **Blocks:**

## Goal
The optional hosted dashboard where a team watches, replays, and **cryptographically verifies** everything their agents did across hosts — sessions list, live terminal stream, event timeline, replay/scrub, a Kill button, and chain verification — the "sell it on a screen" surface. Self-hosted local UI (F3.5) is the trust story; this is the team/multi-host convenience.

## Status — deferred (cross-repo), 2026-08-13
The daemon-side contract this feature needs — a resumable, redacted, hash-chained event uploader with resume-from-acked-seq — is **already delivered and approved in F3.2**. The remaining work (the hosted sessions list, live view, verify badge, and team auth/RBAC) lives in the **separate Opslify web app**, not this daemon repo, so it is deferred out of the daemon's phase scope. P3's self-hosted core (F3.1, F3.2, F3.3, F3.5) shipped without it.

## Scope
**In:** the daemon-side contract that feeds the cloud (the F3.2 uploader + a session-registration/heartbeat), and the dashboard views (sessions list, live stream, timeline, replay, Kill, `opslify verify` surfaced in-UI) on the existing Opslify frontend/backend.
**Out:** the credential broker, policy (later phases); billing; the local UI (F3.5). Trace integrity/redaction come from F3.1–F3.3 — this feature consumes, not reimplements, them.

## Implementation approach
1. **Ingest:** the F3.2 uploader streams redacted, hash-chained events per session to the backend with resume-from-acked-seq; the backend stores them and exposes them to the frontend.
2. **Sessions list:** live state / host / agent / tier / duration across all connected daemons for the tenant.
3. **Live view + timeline:** terminal-style stream of `exec.output` + a structured timeline of `exec.start/end`, `file.write`, redaction markers; replay/scrub of finished sessions.
4. **Kill:** a control-plane signal routed back to the owning daemon to terminate a session (authenticated on the team plane; the daemon authorizes before acting).
5. **Verify in-UI:** surface `opslify verify` results — recompute/verify the F3.1 chain + daemon signature backend-side and show a clear verified/tampered badge, so evidence is provable without shell access.
6. **Auth/RBAC** live here (the team plane), explicitly *not* in F3.5.

## Tools & libraries
The F3.2 uploader (Go daemon), the existing Opslify frontend + backend, SSE, the F3.1 verification routine (shared logic, run backend-side), per-daemon identity for authenticating uploads + kill routing.

## Acceptance criteria (testable)
- [ ] A session on a connected daemon appears in the dashboard with live state; exec output is visible **< 2s**.
- [ ] A finished session replays its full ordered, redacted stream.
- [ ] The dashboard's verify view shows **verified** for an untampered session and **tampered** for an edited one (reusing F3.1 verification).
- [ ] A seeded fake secret is **redacted** in the dashboard (F3.3 upstream — never arrives raw).
- [ ] Kill from the dashboard terminates the live session on the owning daemon.

## QA checklist
- [ ] The backend never receives or stores a raw secret (redaction is upstream in the daemon; verified with a seeded probe end-to-end).
- [ ] Kill is authorized by the daemon, not blindly executed on a control-plane message (no cross-tenant kill).
- [ ] Upload auth uses the daemon identity; a spoofed daemon can't inject events into another tenant.
- [ ] Verification runs on stored events independently — a backend that altered an event would fail its own verify badge.
- [ ] Graceful when a daemon disconnects mid-session (session marked stale, no false "still running").

## Security considerations
- The cloud dashboard is the **networked, multi-user** plane — this is where auth/RBAC/tenant isolation must be enforced, precisely so F3.5 can stay auth-free localhost-only.
- Only **redacted** events cross to the cloud; the backend stores evidence it can independently verify but should treat as sensitive (regulated buyers).
- "We handle your data on our infra" disclosure applies once cloud ingest is on — the self-hosted path (local files + F3.5) must remain a complete alternative with zero cloud dependency.
