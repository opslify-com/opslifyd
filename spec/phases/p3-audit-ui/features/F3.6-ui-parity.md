# F3.6 — Local UI parity (history + verify + approval actions)

**Phase:** P3 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F3.5, F4.3, F4.4 · **Blocks:**

## Goal
Make the whole P3+P4 story **visible and actionable** in the localhost UI: browse and replay **past** sessions (not just live ones), see a per-session **verify** badge, and **approve/deny** gated commands with the dry-run diff in front of you. This closes the gap where the UI showed nothing once a session ended, and turns `opslify ui` into the human-in-the-loop console.

## Scope
**In:** a past-session browser (list + replay ended sessions from the durable trace store), a server-side verify badge, and approve/deny buttons wired to the F4.3 resolve API (rendering the F4.4 preview diff). All localhost-only, behind the existing DNS-rebind Host-guard.
**Out:** the Secrets panel (arrives with the P5 vault — the UI must never show secret values); create-session / run-arbitrary-command from the browser (a separate mutation surface, deferred); multi-user/remote/auth (cloud plane, F3.4). The `opslify top` TUI is not extended here.

## Implementation approach
1. **Past-session browser:** a new READ endpoint (e.g. `GET /v1/sessions/history`) that lists persisted sessions from the F3.2 trace store (session id, start/end time, tier, event count, sealed?), independent of the live `List()`. The SPA gains a "History" list; selecting a past session replays its timeline/terminal from `from_seq=0` over the existing SSE/trace read path. Add the endpoint to the UI proxy allowlist (read-only).
2. **Verify badge:** a `GET /v1/sessions/{id}/verify` endpoint that runs the F3.1 chain+signature check **server-side against the trusted daemon identity** and returns `{verified: bool, events, broken_seq?}`. The SPA shows ✓ verified / ✗ tampered per session (live and historical). (Server-side keeps the daemon pubkey as the trust anchor; the browser just renders the verdict.)
3. **Approve/deny actions:** render the F4.3 `approval.requested` prompt in the UI (it already arrives over SSE) with the F4.4 `preview_diff` shown beside it; Approve/Deny buttons POST to the existing `POST /v1/sessions/{id}/approvals/{exec_id}` with an optional comment. **Add ONLY that approvals-resolve route to the UI proxy allowlist** (it is privileged — see security) — do not open the broader mutation surface.
4. Keep the SPA self-contained (embed, no external assets) and the localhost bind + Host-guard intact; every added route stays behind them.

## Tools & libraries
Go (`embed.FS`, `net/http`), the F3.2 trace store (history listing + replay), the F3.1 verify routine (server-side), the F4.3 approvals API, the F4.4 preview fields on `approval.requested`, the existing `opslify ui` reverse proxy.

## Acceptance criteria (testable)
- [ ] The UI lists **ended** sessions (not only live) and replays a selected past session's full ordered timeline/terminal.
- [ ] Each session shows a **verify badge**: ✓ for an untampered trace, ✗ (with the broken seq) for a tampered one — matching `opslify verify`.
- [ ] A gated command's `approval.requested` (with the dry-run diff) renders in the UI; **Approve runs it, Deny blocks it**, each resolving via the existing F4.3 API and landing in the trace.
- [ ] The UI proxy exposes only: the existing read routes + Kill (F3.5) + the new history/verify read routes + the single approvals-resolve POST — **no other mutation route** is reachable through the browser bridge.
- [ ] Localhost bind + DNS-rebind Host-guard still enforced on every new route (a non-loopback Host is 403).

## QA checklist
- [ ] History listing reads the durable store, not live memory — an ended session survives a daemon restart and still lists + replays + verifies.
- [ ] The verify badge is computed server-side against the trusted identity; a tampered on-disk trace shows ✗ at the right seq (can't be spoofed by the browser).
- [ ] Approve/deny from the UI cannot be reached with a forged Host header (DNS-rebind), and no route beyond the approvals-resolve POST + Kill is mutable via the proxy (enumerate the allowlist in a test).
- [ ] Only redacted data reaches the browser (history replay + preview diff are already F3.3-redacted; no unredacted path added).
- [ ] SPA stays fully self-contained (no external asset fetch); localhost-only bind unchanged.

## Security considerations
- **Approve/deny is a privileged control action.** It inherits the F3.5 localhost-no-auth trust boundary (a local operator) and is protected by the loopback bind + DNS-rebind Host-guard. It must NEVER be exposed to an unauthenticated network — remote/multi-user approval belongs to the cloud/team plane (F3.4) with real auth/RBAC. Adding the approvals-resolve route is the ONLY new mutation; the broader create/exec surface stays closed.
- **Read-only history/verify** add no mutation and only serve already-redacted, integrity-chained data; the verify verdict is computed daemon-side so the browser can't fake a ✓.
- **Explicit GET allowlist (QA fix):** the UI proxy no longer blanket-allows every `GET /v1/sessions/*`. It permits only `history`, `{id}/trace`, `{id}/verify`, and `{id}/approvals/{exec_id}` (all redacted/derived). In particular `GET /v1/sessions/{id}/files` (RAW, unredacted `/workspace` bytes) is refused through the bridge, so a local browser page can never read files the agent wrote. This also closes a pre-existing F3.5 gap.
- The agent still cannot self-approve: the approvals-resolve route is on the operator's localhost UI, not reachable from inside the sandbox.
