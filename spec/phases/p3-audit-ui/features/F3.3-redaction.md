# F3.3 — Redaction v1

**Phase:** P3 · **Status:** todo · **Owner:** Builder (Go) · **Depends on:** F3.1 · **Blocks:** F3.2, F3.4

## Goal
Scrub secrets out of trace event payloads **inside the daemon, before any event is persisted or leaves the process**, so the audit log and cloud dashboard are safe to store and show — a seeded credential must never appear raw on disk, on the wire, or in any UI.

## Scope
**In:** a deterministic redaction pass over event payloads (argv, output chunks, file paths where relevant) for a v1 pattern set + entropy heuristic, replacing matches with `[REDACTED:<type>]`, counting redactions, and sitting in the emit path upstream of F3.2.
**Out:** the broker's real secret handling (P5 — this is defense-in-depth for the trace, not the credential-blindness mechanism); ML/context-aware detection; user-defined rules beyond a config threshold (v1 keeps it simple).

## Implementation approach
1. **Pattern set (v1):** AWS access-key IDs (`AKIA…`) + secret keys, GCP service-account JSON (private_key blocks), `Bearer <token>` / JWTs (`eyJ…`), `password=`/`token=`/`api_key=` assignments, and generic high-entropy tokens above a configurable Shannon-entropy threshold + length floor.
2. **Placement:** redaction is a function the F3.1 sink calls on every event **before** the hash is computed — so the chain commits to the *redacted* payload, and there is no window where a raw secret is hashed, buffered, or written. (The daemon still never logs raws elsewhere.)
3. **Replacement:** substitute the match with `[REDACTED:<type>]` (type = aws-key, gcp-sa, bearer, jwt, assignment, entropy); preserve surrounding structure so output stays readable/replayable.
4. **Counts, not contents:** emit a per-event/per-session redaction count (type-bucketed) for observability; never store or forward the original value.
5. **Config:** entropy threshold, length floor, and an on/off per pattern in daemon config, with safe defaults tuned to minimize false negatives on the known token shapes.

## Tools & libraries
Go stdlib `regexp`, a small entropy helper, the F3.1 emit path. No external deps.

## Acceptance criteria (testable)
- [ ] A **seeded fake AWS key** (and each other v1 pattern) injected via argv/output appears as `[REDACTED:<type>]` in the on-disk log, the SSE stream, and any cloud push — **never raw anywhere**.
- [ ] Redaction runs before hashing: the F3.1 chain verifies over redacted payloads, and no raw secret is ever hashed/persisted.
- [ ] Per-session redaction counts are recorded (bucketed by type).
- [ ] The entropy heuristic catches a high-entropy secret not matching a named pattern, at the configured threshold.
- [ ] Redaction is deterministic — the same input always yields the same redacted output (stable hashes).

## QA checklist
- [ ] No catastrophic-backtracking regexes (bounded, tested against long adversarial inputs — a hostile output chunk can't hang the daemon).
- [ ] Chunked output can't smuggle a secret across a chunk boundary undetected, or this limitation is explicitly documented as a known v1 gap.
- [ ] False-positive rate on ordinary DevOps output (hashes, UUIDs, base64 blobs) is characterized; entropy threshold defaulted to avoid over-scrubbing normal logs.
- [ ] Redaction failure (regex panic, etc.) fails **closed** — the event is dropped or hard-redacted, never emitted raw.
- [ ] Counts never leak the secret (no length/prefix that reconstructs it).

## Security considerations
- This is **defense-in-depth for the audit trail**, not the credential broker: even with P5 credential-blindness, argv/output could echo a token, so the trace must scrub independently.
- **Fail closed:** any uncertainty (regex error, partial match) must bias toward redacting, never toward emitting a possible secret.
- Redaction is best-effort pattern-based — documented as such; it reduces exposure, and the real secret-never-in-sandbox guarantee comes later from P5. Do not overstate it as a guarantee.
