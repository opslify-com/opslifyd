# F2.2 — Session modes (scratch / workspace)

**Phase:** P2 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F2.1 · **Blocks:** F2.3

## Goal
Two session modes: `scratch` (ephemeral, default) and `workspace` (persistent — commit the container FS on end, resume from the latest snapshot on next create), so an agent can build up state (installed deps, cloned repos) across sessions.

## Scope
**In:** `scratch`/`workspace` mode in the session manager + MCP/CLI; snapshot commit on end; resume-from-latest on create; `opslify ws ls|rm`; retention cap.
**Out:** remote/cloud snapshots; cross-host resume.

> **Design note (persistence mechanism):** with the always-on `--read-only` rootfs, the agent's writable path is the `/workspace` **bind mount** — and `podman commit` does **not** capture bind mounts. So the **primary** persistence is a stable per-name **host directory** (`<WorkspaceRoot>/ws-<name>`), kept across sessions and re-mounted on resume (this is what carries installed deps/clones, incl. across a daemon restart — it is just a directory). The rootfs snapshot image (`opslify/ws-<name>:<n>`, with retention + `ws rm` cleanup) is the **secondary** layer: it's committed on end and used as the resume base image, correctly future-proofing a writable-rootfs tier, but under read-only rootfs it captures little. The `workspaceRecord` (snapshot history) persists so restart-resume knows the latest base.

## Implementation approach
1. **`scratch`** (default): destroyed on end (current behavior).
2. **`workspace`**: on `session_end`, commit the container filesystem to a named local image `opslify/ws-<name>:<n>` (via `podman commit` behind the runtime seam). On `session_create({mode:"workspace", name})`, resume from the latest snapshot `:<n>` as the base image (so installed deps persist).
3. **Retention:** keep the last N snapshots per name (config, default 3); prune older on commit.
4. **CLI:** `opslify ws ls` (list workspaces + snapshot counts/ages), `opslify ws rm <name>` (delete a workspace + its snapshots).
5. Extend the `Runtime` seam minimally with a commit/snapshot op if not already present (F1.2 added `Snapshot` to the interface — reuse it); keep it testable against the fake runtime.
6. Snapshots must preserve the hardening posture on resume (the resumed session is still created with the full hard-spec; only the base image FS carries over).

## Tools & libraries
Go, Podman (`commit`), the existing runtime seam + session manager.

## Acceptance criteria (testable)
- [ ] `scratch` session is destroyed on end (no snapshot left).
- [ ] `workspace` session: install something (e.g. a file/dep) → end → new `workspace` create with the same name resumes with that state present.
- [ ] **Workspace session survives daemon restart** and resumes with installed deps intact.
- [ ] Retention cap enforced (only last N snapshots kept; older pruned).
- [ ] `opslify ws ls|rm` behave correctly.

## QA checklist
- [ ] Unit-testable against the fake runtime (commit/resume modeled; retention/prune logic deterministic).
- [ ] Resumed session still carries the full hard-spec (hardening not lost across snapshot).
- [ ] No orphaned snapshot images after `ws rm` / retention prune.
- [ ] (Integration, gated) real podman commit/resume round-trips deps.

## Security considerations
- A resumed workspace is agent-controlled FS state — it is still mounted into a fully-hardened sandbox; the snapshot never carries elevated privileges. **(QA-verified: resume changes only `spec.Image`; hard-spec flags derive from tier + the RO toolchain mounts independently, so a snapshot base image cannot inject flags or bypass isolation.)**
- Snapshot names/paths validated; no traversal or overwrite outside the `opslify/ws-*` namespace. **(QA-verified: `wsNameRe` rejects `/ .. : NUL` etc.; no host-path/image-namespace escape constructible.)**

## Known risks (accepted; best-effort, logged — from independent QA)
- **Untracked orphan image on prune failure:** if `RemoveImage` fails mid-retention-prune, the workspace record is still saved with the trimmed list, so the un-removed image becomes an untracked on-disk orphan (a warn is logged). No state loss. A future hardening could save the record only after successful removal.
- **Untracked image on record-save failure:** if `SaveWorkspace` fails after a successful `podman commit`, the committed image is untracked (disk-failure edge). No state loss.
- **HTTP status nit:** `RemoveWorkspace` of an in-use workspace maps to 400 (`ErrInvalidInput`) where 409 Conflict would read tidier; still legible.
