# F2.2 — Session modes (scratch / workspace)

**Phase:** P2 · **Status:** todo · **Owner:** Builder (Go) · **Depends on:** F2.1 · **Blocks:** F2.3

## Goal
Two session modes: `scratch` (ephemeral, default) and `workspace` (persistent — commit the container FS on end, resume from the latest snapshot on next create), so an agent can build up state (installed deps, cloned repos) across sessions.

## Scope
**In:** `scratch`/`workspace` mode in the session manager + MCP/CLI; snapshot commit on end; resume-from-latest on create; `opslify ws ls|rm`; retention cap.
**Out:** remote/cloud snapshots; cross-host resume.

## Implementation approach
1. **`scratch`** (default): destroyed on end (current behavior).
2. **`workspace`**: on `session_end`, commit the container filesystem to a named local image `opslify/ws-<name>:<n>` (via `podman commit` behind the runtime seam). On `session_create({mode:"workspace", name})`, resume from the latest snapshot `:<n>` as the base image (so installed deps persist).
3. **Retention:** keep the last N snapshots per name (config, default 3); prune older on commit.
4. **CLI:** `opslify ws ls` (list workspaces + snapshot counts/ages), `opslify ws rm <name>` (delete a workspace + its snapshots).
5. Extend the `Runtime` seam minimally with a commit/snapshot op if not already present (F1.2 added `Snapshot` to the interface — reuse it); keep it testable against the fake runtime.
6. Snapshots must preserve the hardening posture on resume (the resumed session is still created with the full hard-spec; only the base image FS carries over).

## Tools & libraries
Go, Podman (`commit`), the existing runtime seam + session manager.

## Acceptance criteria (testable)
- [ ] `scratch` session is destroyed on end (no snapshot left).
- [ ] `workspace` session: install something (e.g. a file/dep) → end → new `workspace` create with the same name resumes with that state present.
- [ ] **Workspace session survives daemon restart** and resumes with installed deps intact.
- [ ] Retention cap enforced (only last N snapshots kept; older pruned).
- [ ] `opslify ws ls|rm` behave correctly.

## QA checklist
- [ ] Unit-testable against the fake runtime (commit/resume modeled; retention/prune logic deterministic).
- [ ] Resumed session still carries the full hard-spec (hardening not lost across snapshot).
- [ ] No orphaned snapshot images after `ws rm` / retention prune.
- [ ] (Integration, gated) real podman commit/resume round-trips deps.

## Security considerations
- A resumed workspace is agent-controlled FS state — it is still mounted into a fully-hardened sandbox; the snapshot never carries elevated privileges.
- Snapshot names/paths validated; no traversal or overwrite outside the `opslify/ws-*` namespace.
