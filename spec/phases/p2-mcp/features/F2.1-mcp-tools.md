# F2.1 — MCP tools

**Phase:** P2 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F1.2 · **Blocks:** F2.2, F2.3

## Goal
Expose opslify sessions to any MCP client (Claude Code first) as tools, over a **thin** layer on the stable internal daemon API — so the agent can create a hardened sandbox, run commands in it, move files, and end it, using only MCP tools.

## Scope
**In:** `opslifyd mcp` subcommand (stdio transport) using the official MCP Go SDK; the five session tools; output caps + truncation; connection to the same Unix socket as the CLI.
**Out:** session modes/snapshots (F2.2); the quickstart doc (F2.3); auth/multi-tenant (later).

## Implementation approach
1. **Subcommand** `opslifyd mcp` (add to `cmd/opslifyd`, or a small `cmd/opslify-mcp` — reuse the daemon's socket client seam from the CLI, `daemon/cmd/opslify/client.go`). stdio transport (stdin/stdout JSON-RPC); the daemon socket path is overridable (`--socket`).
2. **MCP server** via the official Go SDK (`github.com/modelcontextprotocol/go-sdk`). Register these tools with typed input/output schemas:
   - `opslify_session_create({mode, image?, ttl?})` → `{session_id, state}`
   - `opslify_exec({session_id, command, cwd?})` → `{stdout, stderr, exit_code}` — **collect the streamed NDJSON exec frames** from the daemon, apply an **output size cap** per stream (default 1 MiB, configurable) with an explicit `[truncated: N bytes omitted]` marker, and return the aggregated result. (MCP tool results are a single response, not a stream, so aggregation-with-cap is required — never return unbounded output.)
   - `opslify_upload({session_id, path, content_b64})` / `opslify_download({session_id, path})` — base64 file transfer in/out of `/workspace`; enforce a max size; validate `path` stays within the session's writable area.
   - `opslify_session_end({session_id})` → destroy.
3. **Thin over the internal API:** each tool maps to the existing daemon REST endpoints (`POST /v1/sessions`, `POST /v1/sessions/{id}/exec`, `DELETE /v1/sessions/{id}`, and new upload/download endpoints if not present — add them to the daemon minimally if needed, reusing the session manager). Keep MCP-specific logic to schema translation + capping, so MCP spec churn stays isolated (a risk called out in the roadmap).
4. **Error mapping:** surface the daemon's `{layer,error}` as a legible MCP tool error (name the layer), and a clear "daemon unreachable" message.
5. Output/file caps and path validation are security-relevant: a hostile agent must not exfiltrate arbitrary host paths via download or OOM the client via exec output.

## Tools & libraries
Go, **official MCP Go SDK** (`github.com/modelcontextprotocol/go-sdk`), the existing unix-socket client seam, stdlib base64/json.

## Acceptance criteria (testable)
- [ ] `opslifyd mcp` starts an MCP stdio server exposing the five tools with valid schemas (verifiable via an MCP client handshake / `tools/list`).
- [ ] `opslify_session_create` → `opslify_exec` (e.g. `echo`/`ls`) → `opslify_session_end` round-trips against a (fake or real) daemon; exec returns `{stdout,stderr,exit_code}`.
- [ ] Exec output beyond the cap is truncated with a marker; never unbounded.
- [ ] `opslify_upload` then `opslify_download` round-trips a **10 MB** file correctly.
- [ ] download/upload reject paths outside the session's writable area; oversize transfers rejected.
- [ ] A daemon error surfaces as an MCP tool error naming the layer.

## QA checklist
- [ ] Unit-testable against a fake daemon over a temp unix socket (no real daemon/podman/root) — like the CLI's client tests.
- [ ] MCP layer is thin: tools map 1:1 to internal endpoints; no business logic duplicated.
- [ ] Output cap + truncation marker enforced (hostile large output can't OOM the client).
- [ ] Path traversal on upload/download blocked; no secret in tool output/logs.
- [ ] (Integration, gated) Claude Code / an MCP client completes "clone repo X, run its tests, report failures" using only opslify tools.

## Security considerations
- The agent driving these tools is HOSTILE by assumption. Cap exec output, bound file transfer size, and confine upload/download to `/workspace` — no arbitrary host-path read/write via the MCP surface.
- No secret ever returned in a tool result or logged.
