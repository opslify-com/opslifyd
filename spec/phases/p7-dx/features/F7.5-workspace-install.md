# F7.5 — `opslify workspace install <pkg>` (gated, audited, project-local)

**Phase:** P7 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F5.5, F5.8 · **Blocks:**

## Goal
Let the **operator** (never the agent, never a raw `apt` over open egress) install a package into a running session's workspace, with the traffic forced through the **F5.5 registry proxy** (allowlist + attestation + `pkg.install` audit) and the result landing **project-local** in `/workspace` (a venv / `node_modules` / module cache), so "the tool the agent needs isn't in the base image" stops being a dead end — without opening an uncontrolled software-supply-chain hole. This closes the last P7 DX gap.

## Why operator-initiated + proxied
Package install is the classic supply-chain foothold: an agent that can `pip install` anything over open egress can pull a typosquatted or malicious package and run its install hooks inside the sandbox. So install is (1) **operator-initiated** — a human runs `opslify workspace install`, the agent cannot self-install; (2) **forced through the F5.5 proxy** — only allowlisted names, from the configured upstreams, attested when required; (3) **audited** — every install emits a `pkg.install` trace event into the tamper-evident log; (4) **project-local** — into `/workspace`, so it's captured by the workspace snapshot and never mutates the read-only base image.

## Scope
**In:**
- **Per-session registry-proxy wiring** (the F5.5 integration-gated piece): at session create, when the registry proxy is configured, stand up a per-session `regproxy.Proxy` (bound to the session's resolved `creds` grants + trace recorder), bind its listener to the **bridge gateway** (reuse the F5.8 `NetworkInfo` seam + source-IP scope + never-`0.0.0.0` guard), and inject the ecosystem routing env into the sandbox so a package manager resolves through the proxy: `PIP_INDEX_URL`/`PIP_EXTRA_INDEX_URL`, `NPM_CONFIG_REGISTRY`, `GOPROXY` → the gateway proxy address. No credential in the env (the proxy injects the upstream credential server-side, exactly as F5.5 does). Fail-closed: no gateway / proxy not configured ⇒ no routing env, install falls back to "unavailable" (never open egress).
- **CLI `opslify workspace install <ecosystem> <pkg>[@version] [--session <id>]`** — operator-initiated; runs the ecosystem's install command inside the target session (via the existing exec path, so it's policy-checked + traced) with a **project-local target** (`pip install --target /workspace/.opslify/pip` or a venv; `npm install --prefix /workspace`; `go get` into the module). Refuses a package not on the F5.5 allowlist with a clear error BEFORE running. Prints the `pkg.install` audit outcome.
- **`pkg.install` audit event** (the reserved `TypePkgInstall`): emitted per resolved package (name, version, ecosystem, registry, digest, cached?) via the proxy's `emitInstall` into the session trace — so `opslify verify` covers installs too.
- **Ecosystem support (v1):** pip (Python) and npm (Node) as the two proven paths; Go module via GOPROXY if cheap. `apt`/system package managers are explicitly OUT (they mutate the base image / need root / can't be project-local).

**Out:**
- Agent-initiated install (forbidden — operator only).
- Any install path that bypasses the F5.5 proxy or the allowlist (no open-egress `pip install`).
- `apt`/`apk`/system packages into the base image (documented non-goal; a session-scoped overlay for system tools is a future item, not v1).
- Real Sigstore/cosign attestation verification (F5.5 keeps that integration-gated; F7.5 honors `RequireAttestation` via the F5.5 mechanism and does not claim to add real cosign).
- The live end-to-end in-sandbox install over a real bridge (environment-specific, documented manual-test + verified on a live host, like F5.8).

## Implementation approach
1. **Session wiring (`internal/session`):** mirror the F5.7 `EgressInjector`/`egressinject.go` pattern with a `RegistryInjector` (`registryinject.go`): `buildForSession` constructs a per-session `regproxy.Proxy` (F5.5 `NewProxy`), binds the listener to the F5.8 gateway with source-IP scope, injects the ecosystem routing env, and returns a close func for teardown. Opt-in: no config ⇒ no change. Fail-closed on no-gateway.
2. **CLI (`cmd/opslify`):** `opslify workspace install` resolves the target session, checks the package against the F5.5 allowlist (a daemon route or the resolved config), builds the ecosystem-appropriate project-local install argv, runs it through the exec API (policy + trace apply), and reports the `pkg.install` result. A non-allowlisted package is refused before exec.
3. **Audit:** the per-session proxy's `emitInstall` writes `TypePkgInstall` into the recorder — assert an install produces the event with name/version/digest and that it lands in the verifiable chain.
4. **Project-local target:** per ecosystem, target a `/workspace`-relative dir so the workspace snapshot captures it and nothing touches the read-only rootfs; document how the agent then uses it (PYTHONPATH / node_modules resolution).

## Tools & libraries
Go, the F5.5 `internal/regproxy` (`NewProxy`, `emitInstall`, allowlist), the F5.7/F5.8 injection + gateway seam (`egressinject.go`, `NetworkInfo`, `netscope.go`), the exec path, the trace recorder (`TypePkgInstall`). No new dependency.

## Acceptance criteria (testable)
- [ ] `opslify workspace install pip <pkg>` runs an install routed through the per-session registry proxy (unit-tested with a fake proxy/runtime: the injected env points the package manager at the gateway proxy address, never open egress; no credential in the env).
- [ ] A package NOT on the F5.5 allowlist is refused with a clear error BEFORE any install runs; only allowlisted names proceed.
- [ ] Each installed package emits a `pkg.install` trace event (name, version, ecosystem, registry, digest) into the session's verifiable chain (`opslify verify` still passes).
- [ ] The install target is project-local under `/workspace` (captured by the workspace snapshot; the read-only base image is not mutated).
- [ ] The per-session proxy binds the bridge gateway (never `127.0.0.1`/`0.0.0.0`), is source-IP scoped, injects no credential, and is torn down on session end; no gateway ⇒ fail-closed (no routing env, no open-egress fallback).
- [ ] Agent-initiated install is NOT possible (the command is operator CLI only; no MCP tool / in-sandbox path self-installs).

## QA checklist
- [ ] No open-egress install path: without the proxy/allowlist an install is refused, never silently direct to a public registry (fail-closed is BLOCKING if violated).
- [ ] The allowlist gate runs BEFORE the install; a non-allowlisted / typosquat-style name cannot install.
- [ ] No credential in the injected routing env (the proxy injects upstream creds server-side); the per-session proxy binds ONLY the gateway (never `0.0.0.0`), source-IP scoped, torn down on end (reuse/behave like F5.8).
- [ ] Every install is audited (`pkg.install` in the tamper-evident trace) and project-local (no base-image mutation).
- [ ] Agent cannot self-install (operator-only; confirm no MCP/in-sandbox trigger).
- [ ] No regression to F5.5/F5.7/F5.8, F2.2 snapshots, F3 audit; live in-sandbox install honestly documented as integration-gated (not claimed green from a unit test).

## Security considerations
- **Install is a supply-chain trust boundary.** The whole point is that adding a package can't become "the agent pulled and executed arbitrary code from the internet." Operator-initiated + allowlist + proxy + audit are the four controls; none is optional. Fail-closed (no proxy ⇒ no install) beats fail-open (fall back to open egress) every time.
- **No credential in the sandbox.** Registry auth (a private index token) is injected by the proxy server-side, exactly as F5.5 — the routing env the sandbox sees carries only the gateway URL, never the token. This preserves the credential-blind invariant for package installs too.
- **Project-local, snapshot-captured, base-image-immutable.** Installs land in `/workspace` so they're auditable, undoable (F2.2 snapshot / F7.3 sync), and never poison the shared read-only rootfs other sessions boot from.
- **Bind boundary reused from F5.8.** The per-session registry proxy is a credential-injecting listener, so it binds ONLY the bridge gateway + source-IP scope + never `0.0.0.0` — the same trust boundary F5.8 established, not a new weaker one.
