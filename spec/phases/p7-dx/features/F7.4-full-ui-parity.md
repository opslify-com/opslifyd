# F7.4 — Full UI parity (browser can do what the CLI does, safely)

**Phase:** P7 · **Status:** approved · **Owner:** Builder (Go + SPA) · **Depends on:** F7.1, F7.3 · **Blocks:**

## Goal
Bring the localhost browser UI to **parity with the CLI** — create a session, run an exec, manage secret **names** (add / list-names / remove, never values), list/remove workspaces, view the active policy, and **link a host directory + toggle F7.3 sync** — each new mutation reachable ONLY behind the F7.1 launch-token auth + the DNS-rebind Host-guard, with path/sensitive-dir guardrails. "Everything I can do from the CLI, I can do from the browser" — without giving a random web page (or a rebind attacker) any of it.

## Why this is safe now
F7.1 put a per-launch bearer token on every UI route, so the browser surface is no longer "any local page can reach it." That is the precondition that lets us widen `allowedProxyRoute` from read+Kill+approve/deny to the full mutation set: only the operator who saw the launch URL holds the token. This feature does NOT relax the token gate, the loopback bind, or the Host-guard — it adds routes behind them.

## Scope
**In:**
- **Widen the UI `/v1` allowlist** (`allowedProxyRoute`) to also permit, behind the token: `POST /v1/sessions` (create), `POST /v1/sessions/{id}/exec` (run — goes through the SAME F4 policy classifier + approval path as the CLI, no bypass), `GET/POST/DELETE /v1/secrets` (list-**names**, add, remove — the list response is names/metadata ONLY, never a value; POST sends the value once over the token-authed loopback and it is never returned), `GET/DELETE /v1/workspaces` (F2.2 ls/rm), `GET /v1/policy` (read the active `opslify.policy.yaml` view). The raw `GET /v1/sessions/{id}/files` stays **refused** (the F3.5/F3.6 raw-workspace-read hole must not reopen); trace/verify/history/approvals reads unchanged.
- **SPA screens** (`webui/index.html`+`app.js`, still self-contained, no external assets): a create-session form, an exec runner with live trace, a secrets pane (names only + add/remove), a workspaces pane (ls/rm), a policy viewer, and a **workspace-link pane** (pick/enter a host dir, sync on/off toggle, live sync status/conflicts).
- **Directory-linking + sync toggle handled by the `opslify ui` host process** (NOT the daemon): the ui server process already runs host-side, so it hosts the F7.3 sync engine for a linked dir — the daemon never learns the host path, stays portable-minimal. `POST /ui/link {dir, sessionID, on}` on the ui server (token+Host-guarded, a `/ui/*` route the proxy does NOT forward to the daemon) starts/stops an F7.3 `syncEngine` for that dir.
- **Path guardrails on linking:** refuse a sensitive dir (`/`, `/etc`, `/root`, the user's `$HOME` root itself, `/var`, `/usr`, `/boot`, any path containing `..`, a non-existent path, a non-dir, a symlink whose target escapes). The F7.3 secret-exclusion filter still applies to whatever is linked. Arbitrary-path **entry** is allowed only through this guarded endpoint (there is no daemon route for it); a denied path returns a clear error.

**Out:**
- Returning any secret VALUE to the browser (forbidden — list is names/metadata only; the master key / signing key never touch the browser, per F7.1/F7.2).
- Raw `/workspace` file read/download via the browser (`…/files` GET stays refused).
- Remote/multi-user auth, RBAC (cloud plane, F3.4) — this is still the same-machine token trust model.
- Re-implementing sync (F7.3 owns it; F7.4 only drives it from the ui process).

## Implementation approach
1. **Allowlist widen (`cmd/opslify/ui.go`):** extend `allowedProxyRoute` with the create/exec/secrets/workspaces/policy routes above, each still wrapped by `tokenAuthGuard` + `loopbackHostGuard`. Keep `…/files` GET refused. Add a `/ui/*` branch that is served by the ui process itself (never proxied to the daemon) for the link endpoint.
2. **exec parity:** the browser exec hits `POST /v1/sessions/{id}/exec` unchanged — it flows through the F4 pre-spawn classifier + approval gate exactly like the CLI. No new exec code path, no policy bypass. A command needing approval shows the pending state in the UI (reuse the F3.6 approvals poll).
3. **secrets pane:** `GET /v1/secrets` returns `secretMeta` (names/refs/created — the existing value-write-only shape); the SPA renders names only. Add = `POST /v1/secrets` (value typed by the operator, sent once); remove = `DELETE /v1/secrets/{ref}`. Assert in tests the list response has no value field populated.
4. **link endpoint (ui process):** `POST /ui/link` validates the dir against the guardrails, then starts an F7.3 `syncEngine` goroutine bound to `{sessionID, dir}`; `on:false` stops it after a final reconcile. Status/conflicts surfaced via `GET /ui/link/status`. The engine + fsnotify watcher run in the ui process (host-side), never the daemon.
5. **SPA:** add the panes; keep it dependency-free vanilla JS, self-contained (the F7.1 cookie carries auth; no token in JS/localStorage where avoidable). Every fetch is same-origin so the HttpOnly cookie applies.

## Tools & libraries
Go stdlib + the existing `cmd/opslify/ui.go` server, `allowedProxyRoute`, `tokenAuthGuard`/`loopbackHostGuard` (F7.1), the F7.3 `syncEngine`/`wssync` exclusion, the F2.2 workspace routes, the F4 policy/exec path, the embedded `webui/` SPA. No new dependency.

## Acceptance criteria (testable)
- [ ] From the browser (WITH the token) the operator can create a session, run an exec (through the normal policy/approval path), add/list-names/remove a secret, list/remove a workspace, and view the policy — each asserted reachable via the widened allowlist.
- [ ] WITHOUT the token every one of those new routes → 401 (the F7.1 gate still covers them); a DNS-rebind page with a loopback Host but no token is still refused.
- [ ] `GET /v1/secrets` (and any UI response) NEVER contains a secret value; the raw `GET /v1/sessions/{id}/files` is still refused from the browser.
- [ ] `POST /ui/link` starts F7.3 sync for a valid host dir and refuses a sensitive/nonexistent/`..`/non-dir path with a clear error; the sync engine runs in the ui process (the daemon receives no host path).
- [ ] exec from the browser flows through the SAME F4 classifier + approval gate as the CLI (a command needing approval shows pending; a denied command is blocked) — no policy bypass via the UI.
- [ ] No regression: F7.1 token/Host-guard, F3.5/F3.6 (no raw-file read), F7.3 sync invariants (copy-not-bind, secret exclusion) all still hold; SPA stays self-contained (no external asset).

## QA checklist
- [ ] Every NEW mutation route is behind the token (401 without it) AND the Host-guard; enumerate create/exec/secrets/workspaces/policy/link — none reachable tokenless.
- [ ] No secret VALUE ever crosses to the browser (list = names/metadata only); the master/signing keys never in the browser; `…/files` raw GET still refused (the F3.6 hole stays closed).
- [ ] `POST /ui/link` guardrails: sensitive dirs (`/`,`/etc`,`/root`,`$HOME` root,`/var`,`/usr`,`/boot`), `..`, nonexistent, non-dir, out-of-tree symlink all refused; the daemon never receives the host path; the F7.3 exclusion filter applies to the linked dir.
- [ ] exec via UI cannot bypass the F4 policy/approval path (same classifier, same gate) — no privileged shortcut.
- [ ] SPA is self-contained (no external script/style/img/font host); the auth cookie stays HttpOnly; no token in localStorage/logs.
- [ ] No regression to F7.1/F7.2/F7.3/F2.2/F4.

## Security considerations
- **The token is the whole basis for widening.** Every mutation added here is safe ONLY because F7.1 requires the per-launch token; the moment a route is added outside `tokenAuthGuard`+`loopbackHostGuard` it becomes reachable by a malicious local page. Keep them wrapped.
- **Secret values are one-way.** The operator may type a value in to ADD a secret (it goes daemon-ward once over the token-authed loopback and is stored value-write-only), but no route ever returns a value to the browser. Names/refs only. This preserves the F5.6 property under a new UI.
- **Directory linking is the sharp edge.** Arbitrary host-path entry from a browser is exactly the thing to guard: the link endpoint lives on the ui host process (so the daemon never sees the path and can't be tricked), validates against a sensitive-dir deny-list + existence + no-escape, and only ever drives F7.3 (copy-not-bind, secrets excluded). It never bind-mounts, never reads raw files back to the browser.
- **No raw workspace read.** The F3.6 fix (refuse `GET …/files`) stays — parity means the operator's CLI powers, not a new exfil surface for agent-written bytes.
