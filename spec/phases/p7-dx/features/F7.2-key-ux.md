# F7.2 — Key UX (auto-generate + safe storage + one-time reveal)

**Phase:** P7 · **Status:** in-progress · **Owner:** Builder (Go) · **Depends on:** F5.6 · **Blocks:**

## Goal
Kill the vault-key footgun: `opslify init` **auto-generates** the vault master key and stores it where the daemon can read it **automatically** (no more startup fatal, no `OPSLIFY_VAULT_KEY` env dance), while **revealing it once** so the operator can back it up, plus `opslify vault key export` to re-print it for backup. No persistent "download the master key" endpoint.

## Scope
**In:** a key generator + a resolved `KeySource` chain (keyring if available → a 0600 key file → the existing `OPSLIFY_VAULT_KEY` env), `opslify init` generating + storing + doing a ONE-TIME reveal, and `opslify vault key export` (operator CLI, prints once with a warning). The daemon reads the key from the resolved source at startup — the missing-key fatal only fires if NO source resolves.
**Out:** the identity signing key (already auto-generated by init; not touched here); a UI download button for the master key (forbidden — reveal is CLI/one-time only); remote key escrow / KMS backends (documented future).

## Implementation approach
1. **Generate:** `opslify init` mints a 256-bit key (`crypto/rand`) if none exists yet.
2. **Store (resolved chain, most-secure-available first):**
   - **OS keyring** if reachable (Secret Service / Keychain / Credential Manager) — a small keyring lib, used only if present; on a headless server it usually is NOT, so fall through.
   - **A 0600 key file** at a configurable path (e.g. `/etc/opslify/vault.key`, root-owned, NOT beside `vault.db`) — the pragmatic headless default. Documented tradeoff: on-disk means root can read it; for stricter setups use the env or keyring.
   - **`OPSLIFY_VAULT_KEY` env** — still honored as an override (highest precedence, or clearly-ordered), for operators who inject it from a secrets manager.
3. **One-time reveal:** after generating, print the key ONCE with a loud note ("save this in a password manager — it is the ONLY copy; losing it makes vaulted secrets unrecoverable"). Never printed again except via explicit export.
4. **`opslify vault key export`:** an operator CLI that prints the current master key once (with the same warning) for backup. It reads the resolved source; refuse if the key isn't available. This is the ONLY re-reveal path — no API/UI route ever returns it.
5. **Daemon startup:** `buildVault` resolves the key from the chain; the fatal only fires if NOTHING resolves (so a fresh `opslify init` box just works).

## Tools & libraries
Go (`crypto/rand`), the F5.6 `KeySource`/vault (`EnvKeySource`, `StaticKeySource` exist — add `FileKeySource` + optional keyring), the `opslify init`/CLI. A keyring dep is OPTIONAL and must be justified + degrade gracefully when absent; `go mod tidy`.

## Acceptance criteria (testable)
- [ ] After `opslify init` (no pre-existing key), the daemon starts WITHOUT `OPSLIFY_VAULT_KEY` set and without the missing-key fatal (the key is resolved from the file/keyring the init wrote).
- [ ] `opslify init` reveals the generated key exactly ONCE with a save-it warning; it is not printed on subsequent runs.
- [ ] `opslify vault key export` re-prints the current key (with warning) for backup; no API/CLI/UI route other than this ever returns the master key.
- [ ] The on-disk key file is 0600, root/daemon-owned, and NOT in the same file as the encrypted vault; env override still works and takes documented precedence.
- [ ] Missing-key fatal still fires only when NO source resolves (fail-closed preserved).

## QA checklist
- [ ] The master key is never returned by any daemon API/UI route; `export` is CLI-only and prints once.
- [ ] Key file perms are 0600 (refuse/repair looser); the key is not logged/traced; not beside the encrypted vault.
- [ ] Precedence chain is deterministic + documented (env vs file vs keyring); a keyring-absent headless box still works via the file.
- [ ] Rotating/replacing the key doesn't silently orphan existing secrets (either documented or the F5.6 rotation primitive is referenced).
- [ ] No regression to F5.6 (vault encryption, value-write-only) or startup fail-closed.

## Security considerations
- **The reveal is one-time / CLI-only.** Never a persistent download or a UI button — that would be a master-key exfil endpoint on a local-network-reachable surface.
- **On-disk key file is a documented tradeoff** (ease vs "operator holds the only copy"): default for headless ease, but the env/keyring paths remain for operators who want the key off the daemon disk. Be explicit; don't silently downgrade the F5.6 "you hold the key" property without telling the operator.
- **Distinct from the identity signing key** — that one stays on the daemon and is not a casually-exported/passed-around secret.
- Losing the master key = unrecoverable secrets (by design). The one-time reveal + export exist precisely so the operator can back it up.
