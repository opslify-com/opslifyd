# F7.1 — UI launch-token auth (the enabler)

**Phase:** P7 · **Status:** in-progress · **Owner:** Builder (Go) · **Depends on:** F3.5

## Goal
Authenticate the localhost UI with a **per-launch bearer token** (Jupyter-style) so that a page in the operator's browser (or a DNS-rebind attacker) cannot act unless it holds the token printed by `opslify ui`. This is the ENABLER: with auth, the UI can safely gain mutations (parity, directory-linking, secrets) in later F7 features. It does NOT put the audit-signing key in the browser.

## Scope
**In:** `opslify ui` mints a random per-launch token, prints a launch URL carrying it (`http://127.0.0.1:<port>/?token=…`), and the UI server requires the token (a cookie set from the URL token, or an `Authorization`/`X-Opslify-UI-Token` header) on every request — static assets AND the `/v1/*` proxy. A missing/wrong token → 401.
**Out:** the audit-signing identity key (never in the browser); remote/multi-user auth + RBAC (cloud plane, F3.4); mTLS/client-cert (a heavier future option). The new UI mutations themselves are F7.4.

## Implementation approach
1. **Token mint:** on `opslify ui` start, generate a cryptographically-random token (≥256-bit); print the launch URL with `?token=…` (and a plain note). The token lives only in the CLI process + the browser that opened the URL.
2. **Cookie bootstrap:** the served SPA index, when loaded with `?token=…`, sets a `Secure`-style, `SameSite=Strict`, `HttpOnly=false` (JS must send it on fetch) or better an HttpOnly cookie set by the server on the token-bearing request; subsequent same-origin requests carry it. (Pick the approach that keeps the token out of JS where possible — server-set HttpOnly cookie on the `?token` request is preferred; the SPA then just relies on the cookie.)
3. **Enforcement:** a middleware wrapping the WHOLE mux (before the Host-guard or after — both apply) requires a valid token (constant-time compare) on every route; 401 otherwise. Applies to the SPA, the `/v1/*` proxy, and any future route.
4. **Compose with existing guards:** keep the loopback bind + the DNS-rebind Host-guard (F3.5/F3.6). Token-auth is additive — defeats the same-origin malicious-page threat that the Host-guard alone doesn't (a rebind page still lacks the token).
5. **`--no-open`/headless:** print the tokenized URL so a headless operator can copy it; optionally a `--print-url`.

## Tools & libraries
Go stdlib (`crypto/rand`, `net/http`, `crypto/subtle`), the existing `opslify ui` server (`cmd/opslify/ui.go`), the embedded SPA.

## Acceptance criteria (testable)
- [ ] `opslify ui` prints a launch URL containing a random per-launch token; a fresh launch mints a different token.
- [ ] A request WITHOUT the token (no cookie / wrong token) → 401 on BOTH a static asset and a `/v1/*` proxy route; WITH the token → served.
- [ ] The token comparison is constant-time; the token is ≥256-bit random.
- [ ] The loopback bind + DNS-rebind Host-guard still hold; a rebind page without the token is refused (401) even from a loopback Host.
- [ ] The audit-signing identity key is NOT used or loaded anywhere in the UI path (no key-in-browser).

## QA checklist
- [ ] No route is reachable without the token (enumerate: SPA, all `/v1/*`, history/verify/approvals) — a request lacking it is 401.
- [ ] A malicious same-origin page (DNS-rebind, loopback Host, but no token) cannot act — token defeats it (the gap the Host-guard alone left).
- [ ] Token never logged; not in the daemon trace; only in the CLI stdout + the browser. No token in server access logs at info level.
- [ ] Constant-time compare; ≥256-bit entropy; a guessing/brute-force attempt is infeasible.
- [ ] Self-contained SPA + loopback bind unchanged; no regression to F3.5/F3.6.

## Security considerations
- **This is the auth that lets later F7 UI mutations be safe.** Without it, adding create/exec/linking to the browser would be reachable by a malicious local page; with it, only the operator who saw the launch URL can act.
- **Never the audit-signing key.** The identity key signs the tamper-evident trail; loading it into a browser would risk that integrity. Use a disposable per-launch token, not a durable key.
- **Local trust model preserved:** the token is a same-machine secret (printed to the operator's terminal). Remote/multi-user access remains the cloud/team plane's job (F3.4) with real auth/RBAC — this token is not that.
