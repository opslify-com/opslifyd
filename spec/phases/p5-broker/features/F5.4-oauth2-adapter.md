# F5.4 — Tier-2 OAuth2 adapter

**Phase:** P5 · **Status:** in-progress · **Owner:** Builder (Go) · **Depends on:** F5.6 · **Blocks:**

## Goal
One generic OAuth2 adapter, configured per service by YAML, so an operator adds an OAuth2-backed service (`opslify creds add github` → device flow) once and the broker mints **per-request access tokens** for granted sessions — refresh token encrypted at rest, access tokens header-injection-only, never persisted or handed to the sandbox as a value.

## Scope
**In:** a single OAuth2 adapter driven by per-service YAML (auth/token URL, scopes), device-flow onboarding (`opslify creds add <service>`), encrypted refresh-token storage in the F5.6 vault, and per-request access-token minting for injection (via F5.1/F5.2).
**Out:** cloud STS adapters (F5.3), the vault (F5.6), the proxy (F5.2 — this feature provides the token; F5.2/F5.1 inject it).

## Implementation approach
1. **Per-service YAML:** `{auth_url, token_url, scopes, client_id}` — one adapter, many services by config.
2. **Onboarding:** `opslify creds add <service>` runs the device flow; the resulting **refresh token is encrypted** into the F5.6 vault (never printed, never in argv).
3. **Minting:** on a granted resolve, exchange the refresh token for a short-lived **access token**, handed to the injection path (F5.1 env / F5.2 header) — **header-injection only, never persisted, never returned to the sandbox as a value**.
4. **Audit:** `cred.resolve{provider:oauth2/<service>, scope, ttl}` — no token.

## Tools & libraries
Go (`golang.org/x/oauth2` or a hand-rolled device flow), the F5.6 vault, F5.1/F5.2 injection, F3.1 audit.

## Acceptance criteria (testable)
- [ ] `opslify creds add <service>` completes a device flow and stores the refresh token **encrypted** (absent from disk in plaintext, never printed).
- [ ] A granted session gets a per-request short-lived access token via injection — the token never appears in the sandbox as a value.
- [ ] Access tokens are minted per request, not persisted; only the refresh token is stored (encrypted).
- [ ] Adding a new OAuth2 service is config-only (YAML), no code change.
- [ ] `cred.resolve` audited (service/scope/ttl), never the token.

## QA checklist
- [ ] Refresh token never printed/logged/argv'd; stored encrypted via F5.6; access tokens ephemeral.
- [ ] A session not granted the service gets no token (deny-by-default).
- [ ] Token injection is header/env only and never returned to a caller; in-sandbox probe can't recover the refresh token.
- [ ] Device-flow errors fail closed; a revoked/expired refresh token fails cleanly (no stale-token reuse).
- [ ] Per-service YAML validated (bad config → legible error, fail-closed).

## Security considerations
- **Refresh token is the durable secret** → encrypted at rest (F5.6), never leaves the daemon; access tokens are short-lived and injection-only.
- One adapter, many services by config — no bespoke code per provider to audit.
- The sandbox never receives a token as a value in the credential-blind path (via F5.2); env injection (F5.1) is the weaker, documented fallback.
