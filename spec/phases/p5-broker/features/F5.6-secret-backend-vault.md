# F5.6 — SecretBackend interface + local encrypted vault + audit

**Phase:** P5 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F4.1, F3.1 · **Blocks:** F5.1, F5.4

## Goal
The storage + management + gating + audit foundation the whole broker builds on: a pluggable `SecretBackend` (Get/Put/List/Delete), a **local encrypted vault** default impl (values never leave the daemon, never returned to a caller that shouldn't see them), a `opslify secrets` CLI + daemon API to manage them (names/metadata only — **values are write-only from the outside**), enforcement of the F4.1 `creds` policy grants (deny-by-default), and a `cred.resolve` audit event on every use.

## Scope
**In:** the `SecretBackend` interface + a local vault (encrypted at rest, key in the OS keyring / passphrase), secret CRUD (`opslify secrets add|ls|rm` + daemon routes), policy `creds` enforcement (a session may only resolve secrets it's granted), and the `cred.resolve` trace event (name/provider/scope/ttl — **never the value**).
**Out:** the actual injection into a session (F5.1 — this feature only stores + gates + audits), cloud provider adapters (F5.3/F5.4), the L7 proxy (F5.2), the UI Secrets panel (separate small UI feature). Values are never rendered to the UI or logs.

## Implementation approach
1. **`SecretBackend` interface:** `Put(ctx, ref, value, meta) error`, `Get(ctx, ref) (value, meta, error)` — daemon-internal only, `List(ctx) ([]meta)` (metadata: ref/provider/created/ttl, **no value**), `Delete(ctx, ref) error`. This is the battery seam (Vault/OpenBao/ASM impls documented later).
2. **Local vault (default impl):** a SQLite/file store at `/var/lib/opslify/vault.db` (0600, daemon-user), each value encrypted with a data key (AES-GCM / NaCl secretbox) wrapped by a master key from the **OS keyring** (or a passphrase/`OPSLIFY_VAULT_KEY` for headless), envelope-style so rotation is possible. Values are decrypted only in-daemon at resolve time and zeroed after use (best-effort `Zeroize` on the byte slice; documented that Go GC gives weaker guarantees than the plan's Rust target).
3. **CRUD surface:** `opslify secrets add <ref>` (value via stdin/prompt/`--from-file`, NEVER an argv), `opslify secrets ls` (refs + metadata, no values), `opslify secrets rm <ref>`. Daemon routes mirror these; **no route ever returns a secret value** — `Get` is internal to the daemon (used by F5.1 injection), not exposed over the API/UI.
4. **Policy `creds` enforcement (deny-by-default):** F4.1 already parses `creds` grants; here a session may only resolve a secret ref that its resolved policy grants. An ungranted resolve is denied + traced. Reconciles with the F4.1 narrows-not-widens invariant (a workspace can't grant itself creds).
5. **`cred.resolve` audit (F3.1 reserved type):** every resolve emits `{ref, provider, scope, ttl, policy_rule, success}` — **never the value** (and F3.3 redaction still runs). This is the evidence an authenticated action was brokered.

## Tools & libraries
Go, SQLite (or a simple encrypted file store), `crypto/aes`+GCM or `golang.org/x/crypto/nacl/secretbox`, an OS-keyring lib (or passphrase), the F4.1 resolved policy `creds`, the F3.1 recorder (`cred.resolve`).

## Acceptance criteria (testable)
- [ ] `opslify secrets add/ls/rm` manage secrets; **`ls` never shows a value; no API/CLI/UI path returns a value.**
- [ ] Values are encrypted at rest (the on-disk vault never contains plaintext; key in keyring/passphrase); vault file is 0600.
- [ ] A session resolves a secret **only if the policy `creds` grants it** — an ungranted resolve is denied + a `cred.resolve{success:false}` is traced.
- [ ] Every resolve emits a `cred.resolve` event with ref/provider/scope/ttl but **never the value** (asserted: the value never appears in the trace/log).
- [ ] The vault decrypts only in-daemon; a secret value never enters an argv, env dump, the UI, or a log line.

## QA checklist
- [ ] No path returns a secret value to any external caller (CLI/API/UI) — adversarial: try to read a value back; only metadata is ever returned.
- [ ] At-rest encryption is real (grep the vault file for a seeded secret → absent); master-key handling is keyring/passphrase, not a plaintext file next to the db.
- [ ] `creds` deny-by-default holds; a workspace policy cannot self-grant a cred (F4.1 invariant); ungranted resolve fails closed + audited.
- [ ] The value is scrubbed from memory best-effort after use and never logged/redaction-bypassed; `cred.resolve` carries no value/length that reconstructs it.
- [ ] Envelope encryption supports rotation (re-wrap the data keys without re-encrypting every value) — at least a documented path + test of the primitive.

## Security considerations
- **The vault is a high-value target** — encrypted at rest, key in the OS keyring/HSM (not a flat file), 0600, daemon-only. This is the storage battery; a Vault/OpenBao/ASM `SecretBackend` swaps in without changing callers.
- **Values are write-only from outside the daemon** — never returned by any API/CLI/UI. Only the daemon's internal injection (F5.1) decrypts, and only for a policy-granted session.
- This feature does **not** yet make the agent credential-blind (that's F5.1/F5.2 injection) — it is the foundation. Do not overstate: storing a secret ≠ the agent never seeing it.
- Every resolution is audited (`cred.resolve`) so an operator can prove which secret was brokered to which session under which policy, without the value ever touching the trace.
