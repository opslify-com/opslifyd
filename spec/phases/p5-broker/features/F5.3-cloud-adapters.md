# F5.3 — Tier-1 cloud adapters (AWS / GCP / Azure scope-down)

**Phase:** P5 · **Status:** in-progress · **Owner:** Builder (Go) · **Depends on:** F5.1 · **Blocks:**

## Goal
Turn a stored root/source identity into a **scoped, short-lived** cloud credential per session: AWS `AssumeRole` with a session policy, GCP short-lived SA impersonation, Azure federated/managed identity — so F5.1 injects a minimal, TTL-bounded credential, never the long-lived key.

## Scope
**In:** a `CredentialAdapter` seam + AWS/GCP/Azure Tier-1 impls that exchange a source identity for a scoped short-lived credential (scope-down derived from the policy), plugged into F5.1's injection.
**Out:** the injection mechanism (F5.1), OAuth2 (F5.4), the vault (F5.6). Source identity acquisition (instance profile / user CLI session / vault bootstrap) is configured, not invented here.

## Implementation approach
1. **`CredentialAdapter` seam:** `Resolve(ctx, grant, policyScope) (ScopedCred{value, ttl, meta}, error)` — testable against fakes; the real impls call the cloud SDKs.
2. **AWS:** `AssumeRole` with a session policy that scopes *down* from the opslify policy (15-min default TTL); source = host instance profile / user session / vault.
3. **GCP:** short-lived SA impersonation (`generateAccessToken`) scoped to the granted scopes.
4. **Azure:** federated / managed identity → a scoped token.
5. Each returns a TTL-bounded scoped cred F5.1 injects; `cred.resolve{provider, scope, ttl}` audited (no value).

## Tools & libraries
Go + the cloud provider SDKs (AWS STS, GCP IAM Credentials, Azure identity), the F5.1 injection path, F5.6 vault (source identity), F3.1 audit.

## Acceptance criteria (testable)
- [ ] AWS grant → an `AssumeRole` scoped-down session credential (≤ policy scope, ≤ 15-min TTL) injected via F5.1; `aws` works, no long-lived key in the container.
- [ ] GCP grant → a short-lived impersonated token scoped to the granted scopes.
- [ ] Azure grant → a scoped token via federated/managed identity.
- [ ] Scope-down is real: the issued credential cannot exceed the policy scope (adversarial: a broader request is clamped/denied).
- [ ] TTL-bounded; expiry enforced; `cred.resolve` audited with no value.

## QA checklist
- [ ] Adapters tested against stub cloud endpoints (no real cloud needed for unit tests); scope-down + TTL asserted.
- [ ] A grant cannot yield a credential broader than the resolved policy allows (scope-down can't be widened by a workspace).
- [ ] Source-identity handling never logs/leaks the root credential; only scoped derivatives are injected.
- [ ] Adapter failure fails closed (no fallback to a broader/long-lived credential).
- [ ] `cred.resolve` carries provider/scope/ttl, never the token.

## Security considerations
- **Scope-down + short TTL is the containment** — a session gets the least privilege for the least time; the long-lived source identity never enters the sandbox.
- The scope must derive from the (narrowed) policy — a workspace can't widen its own cloud scope (F4.1 invariant extends here).
- Adapter errors fail closed; never degrade to injecting the source/long-lived credential.
