# F5.7 — Broker egress integration (wire F5.2 into live sessions)

**Phase:** P5 · **Status:** approved · **Owner:** Builder (Go) · **Depends on:** F5.2, F5.6 · **Blocks:**

## Goal
Make the credential-blind HTTP path (F5.2) actually work **per live session**, so a granted tool call (e.g. `curl https://gitlab.com/api/v4/projects`) inside the sandbox reaches the real host with the daemon-injected auth header — and the agent never sees the token. This wires the built-and-QA'd F5.2 proxy into the session lifecycle end-to-end.

## Scope
**In:** construct a per-session `egressproxy.Proxy` at session create (with the session's resolved `creds`/egress inject rules + a per-session CA + the broker); start a listener the sandbox can reach; inject `HTTPS_PROXY`/`HTTP_PROXY` + the per-session CA into the sandbox (env + a daemon-written CA file) so `curl`/tools route through it and trust the TLS-terminate; allowlist the daemon→granted-host egress leg; map policy `creds` grants → F5.2 `InjectRule{host, secret_ref, header}` (via daemon config).
**Out:** the F5.2 proxy logic itself (done), the registry proxy (F5.5), non-HTTP egress (stays F1.4 default-deny + DNS-pinned). Real in-sandbox reachability is verified on a live host (integration), not unit tests.

## Implementation approach
1. **Per-session proxy construction:** at `registerReady` (where F5.1 injection already runs), if the resolved policy grants any egress-inject cred, build an `egressproxy.Proxy` for the session (grants → `InjectRule`s from a daemon-config `egress_inject:` list mapping `{host, secret_ref, header_name, header_format}`; F4.1 narrows-not-widens applies), mint the per-session CA, and start a listener on a sandbox-reachable loopback/bridge address (mirror the F5.1 creds-endpoint pattern). Tear down on session end.
2. **Route the sandbox through it:** inject into the sandbox process env `HTTPS_PROXY`/`HTTP_PROXY=http://<proxy-addr>` and `NO_PROXY` for the metadata/creds endpoints. Write the per-session CA PEM to a daemon-controlled path in the session (e.g. `<workspace>/.opslify-ca.pem`, written by the daemon before first exec) and set `CURL_CA_BUNDLE`/`SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`/`GIT_SSL_CAINFO` to it so curl/git/python trust the TLS-terminate. (Agent tampering its own CA file only breaks its own TLS — it cannot extract the token that way; document this.)
3. **Egress reconcile:** the sandbox→proxy leg is loopback/bridge; the daemon→granted-host leg must be permitted by F1.4 (the proxy is the allowlisted HTTP egress path). Non-HTTP stays default-deny + DNS-pinned.
4. **Config:** `egress_inject:` in daemon config (host→secret_ref+header). A grant + a vaulted secret + this rule is what lights up injection for that host. Validate fail-closed at startup.
5. **Audit:** the existing F5.2 `cred.resolve` (valueless) fires on injection; the token never enters the sandbox env/files or the trace.

## Tools & libraries
Go, the F5.2 `egressproxy` package, the F5.6 vault/`Broker.Resolve`, the session manager exec/create path (where F5.1 injection wires in), F1.4 egress, the F4.1 `creds` grants.

## Acceptance criteria (testable)
- [ ] A session granted an egress-inject cred is created with a per-session `egressproxy.Proxy` + listener; the sandbox env carries `HTTPS_PROXY` + a `CURL_CA_BUNDLE` pointing at the daemon-written per-session CA — and **no token** (unit-tested against the fake runtime: assert the injected env, assert the raw secret is absent).
- [ ] The policy→`InjectRule` mapping honors F4.1 narrows-not-widens (a workspace can't add/widen an egress-inject host); an ungranted host gets no proxy rule.
- [ ] Proxy + CA are torn down on session end; a second session gets a fresh CA/listener.
- [ ] `cred.resolve` (valueless) is emitted on injection; the token never appears in the sandbox env/files/trace/log.
- [ ] **(Integration, on a live host):** `curl https://<granted-host>/...` in the sandbox returns the authenticated response, the token is injected at the proxy, and an in-sandbox probe (`env`, files) shows no token — documented manual-test steps.

## QA checklist
- [ ] Per-session proxy/CA/listener lifecycle is correct (built on grant, torn down on end, no cross-session reuse — reuse the F5.2 CA-scoping guarantees).
- [ ] The sandbox env injection carries only proxy addr + CA path, never the secret; the CA file is daemon-written (agent tampering it is self-DoS, not a leak) — tested/documented.
- [ ] Ungranted/unmapped host → no inject rule, F1.4 default-deny still applies (fail-closed).
- [ ] `egress_inject` config validated fail-closed; a workspace can't widen it (F4.1).
- [ ] Non-HTTP egress unchanged (default-deny + DNS-pinned); no regression to F1.4/F5.1/F5.2.

## Security considerations
- **The token is injected at the proxy boundary, never in the sandbox** — env carries only the proxy address + the CA file path. The per-session CA (F5.2) is the trust anchor for the TLS-terminate; its private key never leaves the daemon.
- **Agent-writable CA file is safe:** if the agent overwrites its `CURL_CA_BUNDLE`, its own TLS to the proxy fails — it cannot thereby obtain the token (the token is added by the proxy on the upstream leg regardless of the client's trust store). Document this.
- **Fail-closed:** an ungranted/unmapped host gets no injection and stays under F1.4 default-deny; a proxy/resolve failure injects no header (no raw-secret fallback).
- Real in-sandbox → proxy reachability (podman/gVisor networking, egress allowlist for the daemon→host leg) is environment-dependent and verified on a live host; the wiring + fail-closed behavior are unit-tested.
